## 真实 Lean/Kernel 结果

1. **人工修订文本进入 MathIR**：原识别文本 `l = 1` 被用户修订为 `1 = 1`。测试核实原始文字、规范化文字、block 与 asset 哈希保留；Structure fixture 收到修订后的文本和修订记录，proof-only fixture 返回 `by rfl`。本机 Lean/Kernel 对锁定命题和路线均通过。增加 SourceRef 审计断言后再次运行：`1 passed, 28.37s`；审计基于 5 个 Unicode code point，两个引用范围有效，覆盖 3 个非空白 code point。该案例证明的是校对数据进入 MathIR/Lean 的后端通路，不是真实视觉模型识别，也不是用户原始 Lean proof term。
2. **保留错误方向**：输入 `x≤y`，步骤目标为 `x+1≥y+1`，proof attempt 使用同方向的 `Nat.add_le_add_right`。真实 Lean 拒绝该 proof；步骤状态 `incomplete / not_proved / not_established`，SourceRef 仍指向该错误原步骤。没有构造反例，因此没有报告“数学命题已证明为假”。
3. **正确依赖路线**：自然数 `m≤n` 推出 `m+2≤n+2`。Lean/Kernel 通过，声明的 `source_given` 依赖使用审计为 true，完整原路线通过。
4. **实数同加与反向对照**：同一组实数 `x,y,z` 及前提 `x≤y`，`x+z≤y+z` 通过，步骤依赖审计确认使用 `x≤y`；把目标保持来源位置不变、只按负例构造为 `x+z≥y+z` 后，Lean 拒绝且状态为 `not_established`。两者均保留同一组原文 SourceRefs。未把 proof search 失败解释为反例。

上述三项在一次串行组合中 `3 passed, 96.77s`；校对文本审计断言更新后的单项 `1 passed, 28.37s`；实数同加/反向对照 `1 passed, 42.73s`。组合运行后只更新了测试断言，未修改数学验证生产代码。

构造实数正例时，首个 fixture proof 误用了产生 `z+x≤z+y` 的 Lean 引理，而锁定目标是 `x+z≤y+z`；Lean diagnostics 精确指出两个顺序不同。将测试 proof 改为对应 `x+z` 的引理后，正反对照测试通过。该修正只调整测试中的 proof term，没有更改原命题或验证器规则。
