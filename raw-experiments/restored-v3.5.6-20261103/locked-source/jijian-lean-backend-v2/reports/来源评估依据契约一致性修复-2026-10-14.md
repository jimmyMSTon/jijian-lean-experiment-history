# MathIR v2 来源评估依据契约一致性修复

基线：`1e24c19ed11bfdffd3d4d0bfe788026b29c07784`。

## 根因与修复

来源评估字段允许 `not_assessed`、`ambiguous`、`supported`、`contradicted`、`uncovered`。已有 `Declaration`、`Assumption` 和 `InductionCase` 在运行时要求 `supported` 必须附带 `assessmentBasis`；`Goal`、`RouteNode`、`ProofRoute` 却没有相同校验。Provider JSON Schema 对这几类字段也都未表达这一条件，故相同的“supported”状态可因对象类型不同而接受或拒绝，且结构化输出端无法提前识别缺少依据的结果。

`backend/v2/models.py` 现对六类来源评估对象统一执行同一运行时规则，并将条件写入 Pydantic JSON Schema：当 `sourceAssessment` 为 `supported` 时，`assessmentBasis` 必须存在且非空。重新导出了 `contracts/MathIRV2.schema.json` 与 `contracts/StructureOnlyMathIRV2.schema.json`。没有改动 MathIR 表达式、固定 statement、ProofLock、ProofRoute 依赖语义、Lean Runner 或 Kernel。

旧来源状态测试中两个 `supported` fixture 缺少依据，已补上其显式依据；这是测试数据契约修正，不是放宽运行时验证。

## 验证

- 定向运行时校验、StructureOnly Provider JSON Schema、导出契约一致性：`10 passed`。
- 全非 live / 非 live_ai / 非 lean_local 回归：`523 passed, 26 deselected`；仅有既有 Starlette/AnyIO 弃用警告。
- `compileall` 与 `git diff --check` 通过。
- DeepSeek 请求：0。此修改仅涉及结构校验，未重复 Lean/Kernel 重型矩阵；已有完整 Kernel 案例以先前报告为准，本报告不声称新 Kernel 验证。

## 影响边界

Provider 提交 `supported` 但未解释依据时，会在 JSON Schema 与运行时解析阶段被拒绝；应改用 `ambiguous`/`not_assessed` 或给出来源依据。此项提高来源状态本身的可复核性，但不证明模型语义判断正确，也不证明中文或视觉原文与 MathIR 等价。Kernel 结果和原路线判定不受影响。
