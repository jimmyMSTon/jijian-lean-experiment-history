# 极简 Lean V2｜Mac 原生任务生命周期与错误归因修复

本轮专门检查用户真实操作的提交竞态，不触碰 Codex 正在优化的 Lean、Provider、Repair 后端。

## 定位的产品故障

1. POST /api/v2/jobs 已在后端接受，但用户在网络请求等待期间修改原稿，旧 NativeStore.verify 发现 documentRevision 改变就提前 return，任务 ID 没有保存在 activeJob；服务继续运行时界面却不能追踪或取消，会造成用户看不到任务但有模型费用。
2. POST 已经开始但尚未返回期间，用户修改原稿可触发另一份 POST。旧代码只按输入 hash 防重复；新的输入 hash 不同，会导致并发提交覆盖同一个 activeJob 槽位。当前 UI 只能管理一个任务，其他运行中任务可能被遗弃。
3. 真实 V2 provider 结构化出现 MATHIR_V2_INVALID 时，NativeStore.fail 只显示泛化系统暂时不可用，不告诉用户该错误发生在 Lean 之前，可能误导为原证明被否定。

## 实施的修复

- 仍使用原来的 POST /api/v2/jobs；不增加模型 Gate、定额、轮数、题目限制，也不改变 backend 业务逻辑。
- 在等待 POST 响应时保持 isSubmitting；任何新草稿提交仍使用同一当前可管理的用户任务槽位，待旧提交完成或取消才继续，避免悄悄产生第二份无法取消的模型任务。
- 后端一旦响应带有效任务 ID，立即保存 activeJob、原提交文字和输入身份到 UserDefaults，并启动原 SSE / polling 观察器，即便用户已经编辑了新草稿。旧结果不覆盖修改后的草稿；正在运行时可通过已有菜单取消。
- 对于 MATHIR_V2_INVALID，沿用后端真实说明，明确这是结构形式化失败、尚未经过 Lean 核验，原稿保留；不以数学错题或内核失败标记。
- 系统级网络错误仍按原来的系统提示处理，Lean/Kernel 和原证明判断规则未变。

## 实际测试

- tests/native_v2_job_lifecycle.swift + tests/run_native_job_lifecycle.py：实际编译 NativeStore.swift 和其余原生 Swift 代码（排除正式 App 唯一 @main），连接真实 URLSession 至本机延时 HTTP fixture；在 POST 未返回时 editDraft 并试图再次 verify。
- 观察到后端只接收 1 次 POST，返回的 id 仍在 activeJob 中，旧结果不会覆盖新 draft，可发出唯一的取消请求。随后测试 V2 MATHIR_V2_INVALID 具体错误文案。
- 隔离 CFFIXED_USER_HOME 的 UserDefaults；0 DeepSeek 真实调用，不访问用户实际证明数据库。
- 非实时测试不是完整真实模型 E2E 成功。后续需要继续做真实 GUI 交互、历史恢复等验证。
