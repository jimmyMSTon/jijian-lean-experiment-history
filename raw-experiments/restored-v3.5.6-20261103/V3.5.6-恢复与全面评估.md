## 三、V3.5.6 强项
1. **实际复杂证明能力确实存在。** 对 BMO 数论和两道高联二试不同领域的完整 Lean 形式化命题，旧生成流程得到过不含新增公理的 Kernel 证书；重新重放有效。
2. **有效的整篇 Lean repair。** 当 Lean 报未知名称、类型和 tactic 错误时，LockedProofRepair 让 DeepSeek 根据当前错误修改完整 proofTerm，所有候选必须重新送 Lean。BMO Q5 的成功路径包含 2 次整篇修复。
3. **命题锁定与证据区分。** 已规划的 formalStatement 与后续修改的 proofTerm 分开；证书包含语句匹配、axiom audit；sourceEquivalenceCertified/originalProofCertified 未虚报。
4. **原文位置/推理锚点。** sourceExcerpt 与精确位置匹配；Lean proofTerm 有 source_step_i 标记。来源审计能发现部分具体原稿缺口，例如 2023 高联最小性证明缺少排除所有 k<K 的理由。
5. **错误断言的形式反驳能力。** 在早期 V3.5.3/V3.5.4 同一路线 BMO1 Q3 伪证案例，软件曾对错误局部命题获得 Lean 核验的否定证书；V3.5.6 含该反驳机制。但这不等于任意错误证明均能定位。
6. **桌面工程闭环。** 原生 SwiftUI App、后端任务/历史/取消、诊断、支持文字、LaTeX、图片、拍照、笔迹、PDF、混合输入；独立视觉 LLM 和局部图像复核有实现。正式桌面安装包可运行，Lean 隔离运行并保持审计痕迹。
注意：第 6 点各输入方式均存在实现，但本次没有逐个对图片、手写和 PDF 发起真实付费识别测试，不能据此声称识别精度已经验收。

## 四、重大短板
1. **最本质的产品缺口：形式化定理被证明 ≠ 用户原证明被认证。** 三份成功结果全部 originalProofCertified=false、sourceEquivalenceCertified=false。source_step_i 的名字与原文摘录对齐，并不证明每一步解释忠实、也不证明该步依赖正确。
2. **“AI 帮原证明补出未写步骤”的风险已实际出现。** 2023 高联二试 Q2 的旧版审计标记 suspected_proof_reconstruction_or_gap。原稿只给 K−1 的反例，Lean 补了排除所有 k<K 的推导。数学命题本身可能正确，但不能用这个 Lean 成功认证学生原稿每一步完整正确。
3. **Mac 结果展示存在已复现的分流 Bug。** 后端整题记录 kind=lean_first_local、mode=single_whole_theorem_kernel。V3.5.6 Swift 中 verified 分支误以 kind!=lean_first_local 作为整题前提，因而 BMO 已 Kernel 通过仍 frontendVerified=false；rows 分支仅看 kind，11/11 段被显示为 mappedOnly、0 段 established。通过真实 V3.5.6 BackendClient.swift 与已保存 BMO record 编译运行核对。该误判不撤销 Lean 证书，但影响用户最终页面正确表达。证据：swift-model-check/archived-bmo-parser-evidence.json。
4. **复杂组合/构造/取等问题处理能力不足。** CMO 2023 P4 无法形成完整多引理证明。V3.5.6 主要流程是单个整体 by 证明项 + 整篇修复，缺少通用且可组合的辅助引理证明和可靠上下文恢复机制。这是工程能力边界，不是一个固定题型规则。
5. **成本与时延明显偏高。** 已通过 BMO 案例约 19.3 万 tokens、13.3 分钟；2023 高联约 13.4 万 tokens、10.1 分钟；2025 高联约 8.2 万 tokens、6.7 分钟。失败 CMO 约 8.4 万 tokens、6.2 分钟。实际费用要按供应商当期的思考/缓存计费核算，不能只由 token 总数直接给出准确价格。
6. **生成非确定且对 DeepSeek 输出敏感。** prompt、模型服务端行为、思考 token、Mathlib 名称引用均可能影响是否成功。同一 BMO 原稿在 V3.6.3 真实生成失败；V3.6.5 的缓存重放成功不是新生成能力恢复。现有证据足以归咎于流程改动带来的可重复的风险，但不能排除模型版本或采样差异。
7. **旧接口的兼容与测试维护债。** 6 项遗留测试失败，旧 API 返回 410；虽然符合当时转向 Lean-first 的代码设计，仍增加维护、误判和用户迁移成本。
8. **应用成熟度 ≠ 核验能力。** 布局、相机、历史、导出、审计等功能存在，并不能弥补原稿逐步正确性未被认证；真实 UI 全流程及各图像输入此次仅做启动/后端/存档烟测，不代表全部功能已系统验收。
9. **设备部署偏重。** 原版安装包约 123 MB，配套 Lean/Mathlib Runtime 约 7.9 GB。主机当前存在多份 runtime，占用更大，不能全部归咎于 V3.5.6 单版。

## 五、与后续版本比较
V3.5.6 的整篇修复器是原版最有成功证据的能力：生成整个 by-term → Lean 诊断 → LockedProofRepair 修改完整 Lean 证明 → Kernel 重跑。
V3.6.0 变更了正式整题修复路径，把 LockedProofRepair 的模型输出切为局部 LeanProofPatchBatch。对比真实 BMO 同一原文的 SHA-256：V3.5.6 6 次请求获证；V3.6.3 11 次请求失败。V3.6.5 对同一原文 0 次 AI 请求命中历史成功缓存，因此不能作为新的生成成功证据。
后续新版本的分段诊断、辅助引理、Mathlib 搜索等机制并非必然没有价值，但不能在没有同题对照前声称整体能力改善。

## 六、综合判断
- **恢复成功：** 原版 Mac App、原始干净源码、原版 runtime、数据保护、历史实际 Lean 重放均已核验。
- **最可信的核心价值：** 这是一个可以把部分竞赛级数学定理转成可被 Lean 认证的形式化证明的真实系统。
- **最严重缺陷：** 不能可靠判断学生原稿的每个自然语言步骤是否正确，且旧版 Swift 展示还会误路由整篇证明成功状态。
- **最明显的工程优势：** 旧版完整 Lean 诊断修复路径已经产生复杂题成功样本，比盲目增加新架构更值得当作可对照基线。
- **当前证据无法支持的说法：** 已实现通用奥赛证明检验；已认证自然语言原证明；图片/笔迹识别已达到竞赛生产质量；在未命中缓存时能稳定通过所有曾通过题目。

## 七、备选建议（仅建议，尚未成为用户确认的工程规则）
A. **保留原始 V3.5.6 为不可混淆的可回归基线；若继续开发，在另一条分支修复 V3.5.6 Mac kind/mode 展示 Bug。** 原因：保障旧版证明能力不被后续工作覆盖；影响：需要维持基线与工作分支，开发维护略增。
B. **对原稿各步提供可追溯的独立形式核验，并将“形式化整题成功”“原证明认证”严格分开。** 原因：这正是项目用户价值，而不是又生成了一个正确解答；影响：这是研究级难题，不能保证短期完全解决。
C. **以同一套保存的自然语言题目与相同 Lean 失败候选比较旧整篇修复与新版局部修复，再对照 DeepSeek 不同设置。** 原因：从因果层面区分模型输出和架构退化；影响：真实模型对照会产生额外 token 成本，但比无差别反复生成更有归因价值。
D. **在已有审计字段中清晰展示每次模型请求和 token 消耗、缓存命中与否，并保留曾认证的可重放 Lean 证明。** 原因：帮助控制不必要消耗和辨别新生成成功；影响：会增加可见证据字段，但不应擅自变成阻止正常请求的 Gate。
上述都是建议，未经用户确认，不写入正式产品约束或发布条件。
