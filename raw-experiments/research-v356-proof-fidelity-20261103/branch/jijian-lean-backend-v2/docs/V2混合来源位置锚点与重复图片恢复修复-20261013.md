# 极简 Lean V2｜混合来源固定位置映射与重复图片关联

## 已确认的产品风险

Codex 在 3e942f8 / e7a456e 已将混合图片来源映射补充为 recognitionChildren 中的 partIndex、sourceBlockIds、assetIds；但 NativeStore.restoreMixedSource 仍只扫描各个 pN_ 分区，找到**第一个内容、asset ID 一致**的识别记录就绑定。若一张图片在同一原稿里引用多次，或同一图产生多个已校对识别版本，两个分区可能完全一样但具有不同的 recognitionId。历史子项顺序一变，Native 会把一个分区的识别修订历史错误挂到另一分区，形成错误 provenance，而用户无法察觉。

## 本轮修复

1. 新增 NativeV2HistorySource.matchingMixedPartIndices，根据后端已保存的明确 partIndex 定位来源；同时比对 sourceBlockIds 列表、assetIds、唯一识别 ID、严格的文本/块 ID/页码/bbox 及图片 ID。
2. 如果当前记录同时缺少 partIndex（旧存档），允许使用以前的内容匹配，但**仅在结果唯一时**恢复。两份内容完全相同的旧识别无法唯一确定来源时，拒绝关联并使用原历史原文，不推断，不重新调用视觉模型，也不删除任何片段。
3. 错误或非整数的 partIndex、错误顺序/范围的 sourceBlockIds、资产 ID 列表不一致都拒绝。
4. 此项严格针对来源事实核查，不改 MathIR/Lean、模型 Provider、数学目标、依赖、Kernel、成功语义，也不阻止正常的首次识图或文字证明提交。

## 可复核测试

- tests/native_v2_history_source.swift：两条文字、图片资产、页码均完全相同的来源记录，反转子项读取顺序，验证仍按 partIndex 和 sourceBlockIds 正确匹配各自索引；旧存档没有索引时返回两个候选而不能自动任意选取，错误 ID、资产、索引一律拒绝。
- tests/run_native_mixed_source_recovery.py + tests/native_mixed_source_recovery.swift：对已有隔离 SQLite、真实 Swift NativeStore、签名 App 包内 FastAPI 后端的图片/文字/手写恢复集成，原测试模拟 recognitionChildren 中加入后端真实 partIndex、sourceBlockIds、assetIds 后重新编译运行。
- 全部测试不访问用户真正的识别记录，没有发起 DeepSeek/视觉模型请求，也没有变更旧已存原图。

这个修复的目标是：历史恢复后的 recognitionId 必须对应保存时的精确原稿位置，而不仅是“碰巧具有相同文本”。无法确认时必须保留原稿并明确提示需要重新核对。
