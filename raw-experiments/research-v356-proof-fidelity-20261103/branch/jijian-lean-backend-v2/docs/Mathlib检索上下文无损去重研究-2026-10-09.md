# Mathlib 检索与 Lean 形式化上下文研究（2026-10-09）

本研究使用已有真实本地记录与固定测试输入。没有访问 DeepSeek、没有修改 Lean/MathIR 数学语义，没有改变检索候选集合、数量上限、模型路由或引入新的 Gate。

## 已确认的成本来源

取开发机已有的一个真实简单等式证明工作流（“已知 a=b，求证 a+1=b+1”），其首次 proof 生成调用曾记录 87,644 输入 Token。记录的首次形式化 Mathlib 检索对象约 210,671 字节：

- 声明 64 条（其中 Lean 实际确认 62 条）、源码候选 54 条；
- 重复的成功 `#check` 信息类 diagnostics 约 84KB；
- 同一份源码候选在 `sourceMatches` 和 `declarations[].sourceCandidates` 中重复约 33KB；
- 每条声明重复完整 runtime 环境信息约 20KB；
- 各声明真正有意义的完整 signature 总计约 24.5KB；
- 部分声明是复杂 CategoryTheory 类型，签名本身很长。删除/排名这些声明将涉及新的筛选逻辑，**本轮没有做**。

## 已写入开发工作树的实现

文件：`backend/library.py` 中 `prompt_mathlib_evidence`，以及 `backend/formalization.py` 中生成 proof / repair 时的调用。

- 每条声明、原始顺序、`name`、`found`、`signature`、`status`、所需 import 等都传给 Flash。
- 所有源码候选在 `sourceMatches` 中只出现一次；声明使用 `sourceMatchIndices` 引用同一条记录，未移除任何候选。
- 成功的 `#check` 已经有 `signature`，相同文本不再把冗余 information diagnostic 额外传一次；非冗余 warnings/errors 保留。
- 完整 `retrieval`、诊断原文、运行时信息、来源哈希仍完整保存在原本的 formalization artifact；只对模型输入的 transport 做重复证据紧凑表示。
- repair 同样复用新表示，不改变固定 statement、binder、hash、原证明步骤或已通过片段。

## 测试结果与限制

- 独立开发分支 `codex/next`：普通 pytest `308 passed, 1 skipped`；原基线为 `305 passed, 1 skipped`。
- 三个新增纯本地测试覆盖声明/源码候选无损引用、未索引候选完整保留、非重复警告保留。
- 源码语法检查通过。未执行新的真实 DeepSeek 调用，因此**尚无真实 Token 数、延迟或数学最终成功率差值**。
- 提供不同的 JSON 编码可能影响生成模型的习惯或表现；仅凭字节数下降不能宣布产品性能已提升。没有将此改动合入稳定 `main` 分支或重新打包正式 App。

## 候选后续建议（未经确认，不生效）

1. **建议：** 真实低调用量对照一次，记录实际 `input_tokens`、最终 Kernel 与原文步骤忠实度；好处是验证工程节省是否转化为成本/结果提升，影响是需要付费 AI 请求。
2. **建议：** 在同一份 Mathlib 版本下讨论关键词召回之后的定理候选呈现排序；可能进一步缩短 Token，但任何候选过滤/默认上限会改变信息范围，须征得用户明确确认。
3. **建议：** 将当前 Mathlib 源码索引缓存扩展为跨进程可复用的版本指纹索引；可减少首轮 24 秒扫描，但必须确保版本更新及时失效并保留原检索结果，不作为新门槛。
4. **建议：** 优化 `LibraryPlan` 的上下文复用；在不同 diagnostics 出现时仍正常请求新的 Mathlib 信息，不能用全局离线开关阻断 DeepSeek。
