## 实际发现并整改

1. 混合原稿历史恢复此前只检查每个旧 recognition 块能在保存原稿内找到，即“旧识别是原稿的子集”就可通过。若保存原稿含同一图片来源的第三段，而 recognition 只有两段，重验时使用 recognitionId 会静默丢掉第三段。
2. V2 历史恢复改为**双向完整身份匹配**：每个 pN_ 来源分区必须与其识别记录在 block 数量、唯一 ID、原文片段、assetId、page、bbox 上一一对应。重复 ID、错误页码或不一致区域一律不能冒称恢复成功。
3. 对每个恢复的 recognition 文本，检查保存 recognition.text 是否等于块按原顺序拼接的文字，再检查与完整 mixed source.normalized 一致。恢复不匹配时 NativeStore 抛 SOURCE_MAPPING，由 V2 历史页面显式降级为保存原稿文本及来源关联警告；**不会覆盖任何原稿文字**。
4. 单图 photo、PDF 与手写快照的恢复匹配现在同样检查页码、bbox、原始块 ID 和位置，避免原文一样但图片区域错位仍显示为忠实来源。
5. 发现原 NativeStore.restoreRecognition 虽可取回上一版 recognition，却不持久化 UserDefaults 原稿及 recognition 快照，也不增加文稿 revision。用户在 UI 恢复后重开 App，会重新出现已撤销的识别文本。已修为回退后验证旧记录完整、更新 revision、draft、recognitionEdit、UserDefaults，并明确显示尚未重新验证；混合原稿不会把某一个图片快照当成整个混合输入覆盖。

## 后续同轮发现：手写画布新旧状态污染及识别竞态

- 原 NativeStore.newProof 没有清空 strokes、handwriting 及先前识别编辑状态。新用户原稿重新进入画布时可能连同上一份笔迹一并提交。现已在新建原稿和主动转为自由文本时清理画布及其未识别标志；从历史打开另一份证明也不沿用前一份画布。
- 画布 DragGesture 原先直接改写 store.strokes，既没有增加 documentRevision，也不会令正在处理中的视觉识别结果失效。后端已接收旧 stroke 后再添加新笔画，返回的旧结果可能覆盖最新内容。现在画笔起笔、结束及撤销全部通过 NativeStore 管理，增加 revision、失效旧识别快照及本地来源关联。迟到的识别响应不再覆盖当前笔迹。
- 两次点击“识别手写原稿”在前一请求尚未返回时只允许同一正在进行的请求；不会为同一个手写版本产生并发视觉请求。若当前笔迹已修改而仍未重新识别，按“验证原证明”时只提示先识别及校对最新笔迹，不把旧识别文字当作新手写证明提交。这是**单份原稿来源一致性校验，不是全局 DeepSeek Gate**。
- 单图/手写 restoreRecognition 现在真正持久化上一次识别快照；在识别未完成期间修改手写也不再保留错误的旧 recognition。手写快照附有 originalStrokes 时恢复可用笔画数据。

### 延迟视觉响应实际测试

实际 Swift NativeStore 经 URLSession 连入故意延迟 750 ms 的本地 HTTP fixture。提交首份画布后立刻再次点识别，再在旧响应到达前绘制第二笔；旧识别响应最终被丢弃，但两笔仍保留。通过 UI 层 verify 再调用时没有发往后端的 /api/v2/jobs。NativeStore.newProof 后旧笔画、旧识别来源和未识别状态都被清空。本地 mock 记录 recognition POST=1，proof-job POST=0。与前面图片和手写快照测试一并执行，耗时约 45 秒，全部通过，0 真实 DeepSeek 或 Lean 调用。本轮不宣称真实 Vision 识别正确率。
