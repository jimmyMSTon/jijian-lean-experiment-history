# 原证明忠实性：错误平方推理样本

日期：2026-10-14。样本为本轮新鲜 DeepSeek Flash 文本输入；其原始运行记录、MathIR、调用审计及 proof wire 保存在同目录 JSON。此工作只调整 V2 来源状态与单步状态的后端表达，不改变 MathIR 数学结构、Statement Lock、ProofLock、Compiler、Lean Runner 或 Kernel。

## 修改与回归

`backend/v2/verify.py` 先前没有把 `ProofRoute.sourceAssessment` 和归纳案例的 source assessment 纳入聚合，因此单步明确标为 `contradicted` 时，顶层仍可能显示 `supported`。此外，未决 MathIR ambiguity 只进入 `originalMeaning`，没有进入 `sourceAlignment.status`；被 Kernel 核验的条件步骤却仍被固定标成 `mathematicalStatus=not_established`。

现在顶层来源结果会聚合声明、假设、目标、路线、每个路线节点及归纳案例，并分别返回 `modelAssessment`、`transcriptionStatus` 和 `unresolvedAmbiguityIds`。来源状态将未决歧义显示为 `ambiguous`，人工修订转录显示为 `corrected`；两者都不会声称 Kernel 证明了自然语言/原图等价。路线来源结果也包含同样的转录及歧义字段。单步的 Kernel proof term 经验证后标为 `established`；若其固定义务还依赖原路线前置 claim，则标为 `conditionally_established`；没有 Kernel 证明仍为 `not_established`。

纯 fixture 回归覆盖 contradictory 路线/步骤、未决歧义、人工修订转录及条件步骤标签。随后独立复核发现：完全相同的显式类型量词命题若同时出现在 theorem goal 与 route node（或多个 route node），结构规范化会把对同一 binder 的重复引用误报为词法重用。现在以量词表达式的确定性 SHA-256 指纹区分重复引用和真正冲突：完全相同的绑定共享同一 declaration；同一 ID 对应不同量词表达式仍以 `V2_BINDER_LEXICAL_REUSE` 拒绝。没有推断类型、引入 premise 或改写 statement。此边界有 fixture 测试覆盖 goal/route 重用、多个 route node 重用及不同命题冲突；定向文件回归 `9 passed`（其中真实 Lean 用例未配置 Runtime 时显示 skip，之后用显式 Runtime 单独执行通过）。另补 route 自依赖循环回归，确认以 `V2_ROUTE_CYCLE` 在调用 Lean/Kernel 前拒绝。

最终完整确定性回归命令为 `pytest -q -m 'not live and not live_ai and not lean_local'`：**509 passed、26 deselected**、1 条既有 Starlette/AnyIO 弃用警告。`compileall` 与 `git diff --check` 通过。显式绑定已安装源码指纹 Runtime 后，真实 Lean 4.34 / 独立 Kernel 的量词证明和实数不等式正确/反向对照 `2 passed in 97.39s`；Native V2 HTTP → fixture Structure → Lean/Kernel 合同 `1 passed in 30.99s`。这些 Lean 检查没有访问 Provider。

测试过程中曾错误地执行包含 `lean_local`、却未显式绑定已安装 Runtime 的选择式回归，出现 3 个运行环境相关失败；这不是验收结果。随后正确的标准回归通过，并对需要的 Lean-local 用例显式指定 Runtime 再次执行成功。该情况说明默认 `lean-runtime` 源目录没有 attestation；本轮没有重建、覆盖或修改已安装 Runtime。

## 新鲜 DeepSeek 样本

输入原文：

> 设实数 x、y，已知 x≤y。原证明写道：由 x≤y，两边平方，得到 x²≤y²。因此结论是 x²≤y²。

原文 SHA-256：`e13f1eb7b320d77f755c1b92bc0e58072cc9929b426f0bfdc09ed282e89be68f`。模型为 `deepseek-flash`，无图片。MathIR 保留了 `x≤y`、错误平方步骤和结论，没有增加 `x≥0` 或其他前提；模型还记录了 `amb_square_condition`。固定 statement hash：`0eece1a39a8c6b00cef663dc30d646565818f0fbc946f1b145a2cc1f1c4c0a67`。

该任务的真实调用审计为 3 次：`mathir` 1 次、`formalization` 2 次；输入 **7,493 tokens**、输出 **15,781 tokens**、reasoning **13,790 tokens**，HTTP 合计 **75.681 秒**，端到端 **119.497 秒**。全部为 `retry_index=0`、`cache=miss`、无图片。第一条步骤 `n_square_step` 未取得 proof，来源区间为 Unicode code point `[21,41)`，失败类别为 `missing_proof`，不是 Lean 反例诊断。模型为结论节点生成的片段仅使用 `n_square_step` 作为依赖；该条件片段通过 Kernel，当前代码回放将其标为 `conditionally_established`。错误前置步骤未建立，故固定命题 Kernel=`false`、原路线 Kernel=`false`、路线=`incomplete`。流程在下一次 proof-only 请求没有返回新 patch 后以 `proof_generation_returned_no_patch` 结束，无 LibraryPlan、无 Repair、无 retry。

这说明本样本中系统没有修正原数学方向，也没有把“结论可在假设错误步骤下条件推出”冒充整条原证明成立。未证明本身不会被当作数学反例。来源状态回放为 `ambiguous`，模型结构自评 `supported`，转录状态 `confirmed`，且 `semanticAlignmentKernelProven=false`。

## 独立反例见证

为判断这条错误推理是否有明确数学反例，另行提交固定见证 `x=-1, y=0`：Lean 证明 `-1≤0 ∧ ¬((-1)^2≤0^2)`。该见证不是 MathIR 原路线的一部分，也没有替换其 statement。真正 Lean 4.34 与独立 Kernel 返回 `checked=true`、`statementMatched=true`、`additionalAxioms=[]`，见证路线通过；该独立审计没有调用 Provider。它证明这条普遍推理有反例，但不改变原路线仍未通过的事实。
