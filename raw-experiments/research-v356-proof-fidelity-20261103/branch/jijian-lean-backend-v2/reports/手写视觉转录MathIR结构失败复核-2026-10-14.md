## 通用后端改动

MathIR 类型/作用域错误此前会保存整份 draft 和 SourceRefs audit，但符号越界报错缺少所属表达式路径，业务 API 也不返回该步骤的位置。这使客户端无法把“结构暂不能形式化”稳定映射到原稿步骤。

现在 `backend/v2/typecheck.py` 会在节点、定理、声明、假设和归纳表达式校验失败时补充 owning MathIR path，并在作用域错误中分别记录 declaration scope 与 use scope。`backend/v2/service.py` 将 `validationPath` 以及对应对象已有的 `validationSourceRefs` 放入 `MATHIR_V2_INVALID` 错误详情；draft 中继续保留完整原 MathIR、校验原因和独立 SourceRef 审计。新的回归通过真实 `/api/v2/pipeline` HTTP 入口断言返回字段和来源范围，并确认 Lean runner 未被调用。该改动不修正 MathIR、不改变 statement/前提/依赖，也不会运行 Lean 或把校验失败说成数学错误。

验证：定向结构失败用例 `3 passed`；完整非 live、非 live_ai、非 lean_local 回归 `531 passed, 27 deselected`，有 1 条已有 Starlette/AnyIO 弃用 warning。另用本机已存在且 attestation 与源码匹配的 Lean 4.34 runtime `8ed0581c17efdbc6c9f64ccb66dad3768b4feb21ce25f501aab79b229e7443bd` 执行了真实对照：`test_real_lean_distinguishes_correct_and_reversed_real_inequality_steps` 为 `1 passed, 42.26s`。正确的 `x+z≤y+z` 路线 Kernel 通过；反向 `x+z≥y+z` 保持 `not_proved / not_established`，没有反转原步骤。工作树内无 source-lock 的旧 `.olean` 没有被当成 runtime 使用。`compileall` 与 `git diff --check` 通过。
