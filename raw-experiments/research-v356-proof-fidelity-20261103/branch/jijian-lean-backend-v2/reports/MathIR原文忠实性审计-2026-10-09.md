# MathIR 原文忠实性与语义失真风险审计

日期：2026-10-09  
范围：只读审计 `backend/mathir.py`、`models.py`、`statement.py`、识别与来源定位、`lean/compiler.py`、正式化绑定，以及已有真实录制记录。未修改生产代码、数学判定、Mathlib 检索优化或正式数据；未调用 DeepSeek、Lean 或 Kernel。工作树中既有 UI 修改保持不动。

## 结论

当前链路能较好地**固定并复核已经结构化的命题**：MathIR 表达式由代码生成 canonical statement、Binder Map 和 Statement Hash；proof 阶段只返回 proof body；Lean diagnostics 与 Kernel 核验的是这个固定命题。它不能证明初次转录、MathIR 自然语言字段和 AST 忠实于用户原文。源码中的 `semanticAlignment` 明确标为 `typed_mathir_statement_locked_natural_language_alignment_not_kernel_proven`（`backend/formalization.py:93-95`）。因此，内核通过证明的是 AST 锁定后的 Lean 命题，不是原文到 AST 的翻译。

对纯文本，首次语义失真风险在 `UnderstandingService.structure()` 的 `SemanticMathIR` 调用（`backend/mathir.py:127-135`）：之后的验证主要检查结构和可形式化性，没有独立的原文语义对照。对图片/手写，风险更早，在图像转录与视觉复核产生的 `normalized` 文本；未被视觉阶段发现的漏字、符号或条件会进入 MathIR。后一阶段若忠实翻译了错误转录，也无法由 Kernel 检出。

## 数据链与现有保障

1. **输入/转录。** `RecognitionService.resolve()` 对文本保留 `raw=normalized=input text`；对图像/手写保留转录原文、规范文本、recognitionId 和 source blocks（`backend/recognition.py:173-215`）。`FlashRecognitionService` 会存原始转录、裁剪转录和视觉差异/歧义；用户更正另存修订证据（`backend/flash_recognition.py:41-73`、`backend/recognition.py:217-236`）。这些信息提升可追溯性，但不能证明转录覆盖了原图中的每个数学语义。
2. **MathIR。** 服务端把完整 Source 和哈希传给 `SemanticMathIR`；模型返回变量、定义、假设、证明步骤、目标、依赖、作用域、歧义和形式 AST（`backend/mathir.py:127-155`）。提示词要求保留前提、符号、证明路线、局部作用域和歧义（`backend/mathir.py:7-40`），但提示词是模型要求，不是验证证据。
3. **结构校验。** `validate_mathir()` 检查根/父作用域、重复 ID、sourceRef 的 block 和范围、依赖 ID、局部假设可见性、循环依赖及归纳结构（`backend/mathir.py:44-87`）。它不检查引用范围实际支持该字段、不检查所有原文片段均已被表达，也不比较 `Claim.text` / `latex` 与 `formal.expression` 的数学含义。
4. **命题锁定。** `canonical_plan()` 从 typed AST 导出 Lean 类型、前提、量词和目标；检查 AST arity、符号存在、类型及作用域，随后计算哈希（`backend/statement.py:97-156`）。`Compiler` 以此创建固定义务与 proof-only 接口（`backend/lean/compiler.py:24-50,181-216`）。之后的锁定有效，但不回溯证明初始 AST 与原文相等。
5. **位置映射。** MathIR sourceRef 使用 Unicode code point offset（`backend/models.py:8-12`）。Lean obligations 保存步骤 sourceRefs；sourceMap 标记 `statement_level`（`backend/lean/compiler.py:166-172,195-215`），diagnostics 的 mappingPrecision 是 `step`（`backend/lean/diagnostics.py:27-32`）。当前可以诚实映射到原文块/步骤，不能据此声称定位到了图片里的某个字符或笔画。

## 按字段的忠实性审计

| 对象 | 当前数据与保护 | 仍未证明的内容 / 具体风险 |
|---|---|---|
| 原始条件与 assumptions | `Claim` 保存 text、latex、scopeId、sourceRefs；canonical theorem 外部前提来自 MathIR assumptions，不会由 proof response 静默添加（`models.py:58-67`、`statement.py:129-140`）。 | 没有通用机制比较每个 root assumption 是否真的出现在题目条件中。数学等价的改写、漏掉条件、把证明内引用提升为前提，都可能通过字段/范围结构检查；当前仅有下文的平方中文特判。 |
| 变量与类型 | `Variable.domain` 保存模型给出的域，Canonical Binder Map 固定为 Lean type（`models.py:43-49`、`statement.py:17-23,101-104`）。 | 域和值的来源没有语义校验；“题设给定”不能替代具体类型。实际正整数样例写作 `\mathbb{N}^+` 或“正整数集 N*”，当前 alias 表没有该项；需要表达为 ℕ 与 `n>0` 条件或适当 subtype，但当前 data model 没有通用的“对象类型 + 域谓词”关系。不得因此把正整数等题型排除。 |
| 量词与目标 | AST 支持 `forall`、`exists`、连接词等，binderId 必须引用变量；canonical plan 从 AST 生成 theorem（`models.py:78-94`、`statement.py:56-84,141-147`）。 | 没有校验自然语言目标/latex 中的量词、量词顺序、自由变量与 AST 相符。AST 即使合法，也可能漏掉 `∀θ`、把给定参数变为量化变量、或改变 `∃P` 与 `∀θ` 的次序。 |
| 证明步骤 | `Step` 保存 text、latex、reason、dependsOn、scopeId 和 sourceRefs；依赖 ID 有向图可查环（`models.py:58-67`、`mathir.py:74-87,101-116`）。 | 没有原文覆盖率或文本步骤到 AST 的语义一致性检查。AI 可将多步合并、拆分、遗漏“因此”等桥接，或创建有合法 sourceRef 但数学表达不同的节点；Lean 只检查 AST 对应的独立义务。 |
| 依赖与局部假设 | 直接依赖必须指向 assumptions/proofSteps；局部 assumption 不能从其 scope 外被直接依赖（`mathir.py:74-85`）。带 `inductions` 时会校验 P(0)、P(n+1)、∀n P(n) 结构及局部假设范围（`mathir.py:164-219`）。 | 依赖是否忠实反映原证明推理，未由源文本验证。旧归纳记录可把归纳假设列成 proofStep；缺少 `inductions` 时只靠“reason 含归纳假设、text 以假设开头”这一中文词面启发式检测（`mathir.py:164-169`），其他语言/措辞/节点类型可绕过。 |
| 定义/多项式对象 | AST 可表达 add/pow/eval/apply 等；Binder Map 会固定多项式定义值（`models.py:78-94`、`statement.py:105-112`）。 | 表达式 AST 的 op 集合是固定核心，不含许多通用数学构造器（例如集合隶属、积分、极限、矩阵/向量、导数、分段函数）；一些常量/函数应用可表达部分情况，但不保证有类型和 renderer 支持。不能把这当成题型白名单。 |
| 图片来源位置 | SourceBlock 可保存 page、bbox、confidence、assetId、providerData（`models.py:20-27`）。图像块的 prompt 要求 block-level ref（`mathir.py:12-14`）。 | 手写录制样例 `tests/fixtures/deepseek/handwriting_case_01.json` 的 16 个 block 均 `page=null`、`bbox=null`，`locationPrecision=reading_order_only`。其 providerData 中的 `formulaRegion` 是模型估计区域，不是字符级标注；裁剪代码也标记 `model_estimate_with_padding` / `pixel_row_estimate_not_text_alignment`（`backend/transcription.py:19-27,180-188`）。MathIR 变量常引用整块，例如 `corrected_factor_mathir.json` 中 n、θ、x 都引用 b0 的 `[0,83)`。这是整行/块级关联，不是变量字符精确定位。 |

## 现有录制样例对照

### 手写三角多项式样例

- 真实录制图像转录 fixture 标为 `recorded_real_response`，重放说明为 offline replay；它不是本轮新识别或 Kernel 运行。识别文本保留了法 1 的前导 `2`，且视觉证据记录了法 2 连笔汉字、`整系数`字样、乘号点等仍未确定事项；corrections 数为 0，歧义未强行应用。文件：`tests/fixtures/deepseek/handwriting_case_01.json`。
- 后续录制 MathIR `tests/fixtures/deepseek/corrected_factor_mathir.json` 的 source 保留同一原图 asset 与 raw/normalized；把 `n` 写作 `\mathbb{N}^+`，θ 域写“未明确写出”，P 与 x 的类型/绑定仍是文本定义；`formal` 和 `inductions` 均缺失。多个变量 sourceRefs 指向题目整行，而不是符号子串。这说明原稿/识别证据存在，并不自动令 MathIR 已有可锁定的数学 AST。

### 奇数求和归纳样例

- 原输入在 `reports/statement-lock-three/induction.json` 中有“题目→基例→假设 P(n)→后继 P(n+1)→归纳总结”的完整文本。保存的初始 MathIR 把 `step_ih` 放在 proofSteps；`inductions` 缺失。其旧形式化记录因此不具备正确的局部假设角色。

## 不能泛化的特判与具体缺口

1. **平方非负 + 中文词语 + 固定分隔符特判。** `canonical_plan()` 仅当 raw 含 `【证明】`，root assumption.text 同时含“平方”“非负”，而分隔符之前文本没有这两个词时拒绝（`backend/statement.py:129-138`）。英文、公式 `x²≥0`、无该分隔符或其他由证明中引用而被提升的已知事实都不受同一语义保护；反过来，仅凭文本模式也不能证明 assumption 来源非法。
2. **归纳漏标检测是题面语言启发式。** `validate_inductions()` 在没有结构时只识别特定中文 reason/text 开头（`backend/mathir.py:164-169`）。已有显式 `Induction` 的验证更强，但它当前只表达自然数简单归纳 P(0)/P(n+1)，不覆盖强归纳、良基归纳或其他递归结构。
3. **多项式定义类型推断基于名称/关键词。** `canonical_plan()` 依据定义名匹配变量，或依赖 `多项式`/`P(` 文本正则推断 `Polynomial ℝ`（`backend/statement.py:105-112`）；这不是一般的定义类型系统，可能漏掉别名/非中文表述，也可能把同名定义错误绑定。
4. **schema 与运行期必需条件不一致。** `MathIR.formal` 和 `SemanticMathIR.formal` 声明为 optional（`backend/models.py:115-136`）；`validate_mathir()` 在 formal 缺失时仍可成功返回结构（`backend/mathir.py:150-155`），但正式化的 `canonical_plan()` 会拒绝缺少 typed expression 的 IR（`backend/statement.py:97-100`）。结果是“structure 成功”不保证结构已达到当前正式化契约；需要明确是让 structure 保存非正式化草稿，还是让 canonical formal 成为结构返回的必需条件。两种选择会改变 data/API 行为，当前不代为选择或改代码。
5. **AST 表示覆盖不均。** `MathExpression.op` 列表与 renderer/typechecker 是封闭的结构核心（`backend/models.py:78-94`、`backend/statement.py:53-84,281-326`）。现有实测中的归纳求和、三角函数、多项式有相应节点，但这不能推出数学对象/推理形式已普遍覆盖。通用扩展要保留原式与未知节点，不能通过题型白名单解决。

## 通用方案（供确认，不在本轮实施）

### 不改当前命题判断的只读审计层

- 为每个 MathIR 节点建立证据账本：原文片段/来源块、raw 与 normalized 版本、节点类别（题设条件/变量域/定义/原文步骤/派生关系/局部假设/总目标）、节点表达和当前是否有未决歧义。已有 sourceRefs 与 transcriptionEvidence 可作为输入，账本需区分“位置合法”与“内容确实支持此语义”。
- 用可逆的 segment coverage 检查原文中与数学相关的 span 是否被变量、条件、定义、步骤、目标或明确的非命题方法文字覆盖；未覆盖、重复指向、空范围、跨块/整页泛指仅产出审计差异，不擅自改 node 或 Kernel 判定。
- 对存在 `formal.expression` 的节点，用 typed AST renderer 生成规范表达，再把 `text`、`latex`、source span 与规范表达并列供审计。对确定性可解析的数学子集可以比较 AST；自然语言仍不能被该比较覆盖，必须保留“未验证语义等价”的状态，不应宣称机器自动证明了忠实性。
- 图片位置只采用真实 OCR region/bbox、page 和坐标变换链；估计的 `formulaRegion` 标出 estimate。没有源坐标时维持 block/step 级映射，不从文字位置或裁剪窗口反推精确字符坐标。

### 需用户确认后才能进入正式产品的变更

- 是否令 `formal` 成为 `/api/structure` 的必需字段，还是允许结构化草稿单独成功并公开清晰的“尚未形式化”状态；这是 schema/API 契约与状态语义变化。
- 是否扩展 MathIR 为对象类型 + 域谓词/量词约束，补齐正整数等类型表达；以及是否将 `Induction` 泛化为可引用 Lean induction principle/case schema。它们改变数据契约与 formalization 输入。
- 是否加入额外语义对照记录/审计状态及其 UI 表达。任何“差异导致拒绝/必须人工通过”都会改变产品行为；未确认前只建议作为可观察性研究，不作为 Gate。
- 是否扩展 typed AST 的 operator/type renderer 以保留更多数学构造。扩展应按对象/运算逐项保持原式与 source evidence，不新增题型界限，不修改现有 Kernel 判断。

本报告不要求或触发新模型、新请求次数规则、人工审核、Mathlib 过滤、题型限制或重新实现 Mathlib 去重。现有无损检索上下文去重保留；本次没有执行任何 AI/Lean live 检查。
