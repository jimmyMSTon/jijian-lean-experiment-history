# MathIR 通用化与原文忠实性研究（2026-10-10）

## 结论

当前系统有一条边界清楚的形式验证链：typed MathIR 导出固定 Lean theorem，Statement Lock/Binder Map/Statement Hash 固定该 theorem，Lean 检查 proof，独立 data-only Kernel 复核证明对象。它能回答“这个证明对象是否证明了这个固定的 Lean 命题”，但不能单独回答“识别结果和 MathIR 是否忠实表达了用户原文”。现有审计与记录一致支持这一结论。

本轮没有修改 MathIR schema、成功状态、Statement Lock、Binder Map、Mathlib Retriever、Lean、Repair 或 Kernel，也没有发起研究性 DeepSeek 请求。全量 pytest 意外收集了两个 `live_ai` 测试：测试环境存在非空占位凭据，导致两次真实 HTTP 尝试，均返回 Provider 错误；request audit 证实两次 `retry_index=0`、无 token usage、各只有一次请求，没有重试。发现纯数字 `1/2` 在缺乏类型上下文时会被确定性地推成 `ℕ`，但 MathIR 没有表达作者希望使用 ℚ/ℝ 的字段；这不是可安全靠默认值修复的 bug，需改 typed literal/type contract。没有其他可在不改变数学契约的前提下应立即修复的缺陷。凡涉及 MathIR 类型/作用域表达或正式成功语义的改动，先由用户确认设计，再实施。

## 证据分层

应把一次验证中容易混淆的五个问题分开记录：

| 层 | 可回答的问题 | 不能据此声称 |
|---|---|---|
| 转录 | 系统保存了什么原文、规范文本、来源块与歧义 | 转录完整或每个符号都正确 |
| MathIR 忠实性 | AST、变量域、定义、条件、步骤与来源片段是否相符 | 当前结构校验通过即等于语义忠实 |
| 固定定理 | Compiler 从 MathIR 导出的 Lean statement、binder 和 hash 是什么 | 该 statement 等价于原题 |
| 步骤证明 | 每个原证明步骤对应的 Lean obligation 是否建立 | 任一通过步骤即代表整份证明通过 |
| Kernel | 独立复核器是否确认 proof object 建立锁定的表达式 | Kernel 替用户判断了自然语言与形式命题是否等价 |

识别若漏掉条件，或 MathIR 把证明中的事实提升成题设，后续锁定和 Kernel 都可能完全正确地验证了“错误翻译”。这种结果必须称作“锁定命题已验证”，不能扩大为“原文证明已忠实验证”。

### 录制的双方法归纳页：结构证据细化

`formalization_case_01.json` 中原始 MathIR 保存了完整页文本，但 `formal` 与 `inductions` 均缺失。变量 `n` 的域文本为“正整数集 N*（题设给定）”，`θ` 和 `x` 的域写成未明确，`k` 在归纳作用域中；定义列表为空，尽管题目说 `P(x)` 是多项式。局部 assumption `asm-ind` 位于归纳 scope，说明来源模型至少表达了作用域位置，但缺少 induction node 将它和变量、基例、后继 case、全称结论关联起来。

同一页有“法1”和“法2”，但旧 MathIR 把法1错误公式保存成独立 `proofStep`，法2步骤另列为同一证明图，最终目标依赖法2结束语。Compiler 为所有步骤产生 obligation，整体验证要求每个片段存在才能组合 aggregate；法1缺失证明因此会阻止整页 aggregate，即使另一方法路线可以建立目标。这不是 Lean/kernel 缺陷，而是当前 `proofSteps`/`dependsOn` 没有表达“备选证明路线”的契约限制。通过把其中一条方法删掉来提高通过率，会改写用户原证明；正确方向是未来经确认后让证明路线成为明确的选择/分支结构，且仅对选定路线汇总证明，同时仍保留其他路线的原文与状态。

历史形式化记录把 `n` 绑定为 Lean `ℕ+`，`θ` 取 `ℝ`，还把未在结论中使用的 `x` 作为 `ℝ` binder；更关键的是，录制的总目标包含一个由 proof dependency `s9` 引入、其类型含全称量词和 IH 的引理。该结果 `statementChecks=elaborated` 只证明生成的 Lean 类型可 elaboration；整份记录 `kernelVerified=false`、aggregate 为 null。由于该录制 MathIR 没有当前 canonical pipeline 必需的 typed formal AST，这份旧 formalization 不能当作当前 Compiler 在现行 MathIR 契约下重新生成的证据。

另两份录制物揭示定义/来源和绑定的共同缺口。`corrected_factor_mathir.json` 有 2 个定义（实系数目标多项式与整系数辅助多项式）、5 个变量和 2 个 assumption，但 `formal` 为空；`formalization_binding_failure.json` 把辅助多项式类型选择、系数环到 ℝ 的映射、θ 的实数域和 `Δ` 分母歧义写在自然语言 translation notes 中，却仍没有 MathIR typed AST，并以 `FORMAL_BINDING_MISMATCH` 结束，Lean 未运行。这是合适的失败结果：类型/对象绑定不完整时不能让 proof text 补出声明。与此同时，来源不能支持这一类型选择：文本“整系数多项式”的 definition 是有意义的数学定义，不应仅保存为普通 `Definition.text` 后再由自由格式 notes 决定 Lean type。

这组记录还包含未决原文（分母候选 `Δ/A/4`、符号/因子行差异）和已确认的错式。`whole_page_consistency_missed_factor.json` 的旧视觉复核曾报告没有明确视觉差异；与后来固定 MathIR 中保留的多余 2 合看，说明“多轮/整页视觉未发现差异”仍不是从原图到 theorem 的形式化证书。对此类输入，未决歧义和来源范围应作为证据状态保留，不能选择一个能通过 Lean 的读法来回填原文。

本轮实现并运行了只读 ledger 原型 `devtools/research/mathir_fidelity_ledger.py`，对 `formalization_case_01.json`、`corrected_factor_mathir.json`、`formalization_binding_failure.json` 生成逐节点/逐 sourceRef 的 JSON 证据。结果：三份记录均有 16/16 个 source block 被至少一个合法引用覆盖，非法/越界 ref 为 0；未决 ambiguity 数分别为 13、6、19；typed expression 缺失数分别为 12、15、14；三份都被现行 `canonical_plan` 以 `STATEMENT_DRIFT` 拒绝，原因是“MathIR 缺少类型化数学表达式”。其中两个样本 raw 与 normalized 不同。即便 ledger 看到全部 block 被引用，也明确只报告词面 span 覆盖，不推断 claim 与原文语义相符。机器结果保存在 `reports/mathir-fidelity-ledger-recorded-2026-10-10.json`；该 JSON 被仓库 `.gitignore` 的 `reports/**/*.json` 忽略，Markdown 中保留汇总结果。

### 新增数学证明样本：有限几何级数归纳

未参与此前 Mathlib 证据组织优化的 `fraction_proof_first_recorded.json` 中，第二道题给出 `∑_{k=1}^n 1/2^k = 1 - 1/2^n`，并写出基例 `n=1`、局部归纳假设和 `n=k+1` 步骤。原录制转录仍混有上一题立方和及疑似阿拉伯文旁注，所以这里只把这条可辨认的几何级数公式当作数学结构研究样例；没有声称整页转录忠实，也没有向 Provider 重发图片。

当前 `sum_range` 可以表达 `k=0..n-1`，于是索引平移后的 AST 可将用户的 `k=1..n` 写成 `i=0..n-1` 且 summand 使用 `1/2^(i+1)`。但对没有上下文类型的 `1/2`，当前 `expression_type` 确定性地默认推为 `ℕ`；给定期望类型 `ℚ` 才会推为 `ℚ`。我用 canonical compiler 对 `n : ℕ`, `0<n` 和该 `sum_range` AST 生成的锁定 statement 确实是自然数除法版本，不是通常的有理数有限和。实际 Lean/Mathlib 本地检查确认 `(1 : ℕ)/2 = 0`，而 `(1 : ℚ)/2 ≠ 0`。因此在数值类型未显式声明时，结构 AST 可编译并被 Statement Lock 固定，却可能与原来通常意义的分数表达不一致；Kernel 只会对锁定的这个类型负责。

该样本还有一个独立的归纳边界：原稿从正整数 `n=1` 起步，当前 `validate_inductions()` 固定要求基础表达式为 `P(0)`、总结为 `∀ n, P(n)`。我对已通过的归纳 fixture 做了隔离变体，将基例表达式改成 `P(1)`；当前 validator 明确以 `IR_INDUCTION_STRUCTURE: 基础情形不是原命题的 P(0)` 拒绝。原稿的正整数目标应保持 `∀ n : ℕ, 0<n → P(n)`，并通过起点 1 的归纳原则验证，不能为适配验证器将原证明伪造成从 0 开始。

因此此新样本在本轮的状态为：原文记录有页面级不确定性；公式子串可供研究，但本轮没有确认图像/转录准确；MathIR AST 可编码区间求和形状，但当前数值类型推断对纯数字分数不忠实；当前 theorem 若锁成 ℕ 除法则与预期数学命题不同；未构建用户证明步骤，也未对该几何级数目标运行 Kernel。它暴露的是 typed literal 与带起点归纳表达能力缺口，而不是模型能力结论。

来源与范围：三题记录见 `reports/three-confirmed-fixes/三题修复与FlashLean能力报告.md` 及同目录 JSON；原文忠实性审计见 `reports/MathIR原文忠实性审计-2026-10-09.md` 和 `reports/MathIR审计独立复核-2026-10-09.md`；独立手写转录 fixture 为 `tests/fixtures/deepseek/fraction_proof_first_recorded.json`；正整数手写链为 `tests/fixtures/deepseek/repair_case_01.json`；输入修订证据见 `reports/真实错误证明与修改闭环V1-2026-10-10.md`。历史证据并非同一运行环境下的统一重放，本报告不把它们冒充严格横向基准。

## 当前实现的结构性边界

1. `MathIR.formal` 可选，节点保存自然语言/LaTeX 与 typed AST，但 `sourceRefs` 当前主要验证 block/range 存在，不验证引用内容是否支持节点语义，也不检查数学原文覆盖是否完整。生产 `Services.structure()` 会在存储成功结果前运行 Compiler；因此 schema 中可选不等于正式化链可接受无 formal 的 MathIR。
2. `Variable.domain` 是自由文本后映射到有限 Lean 类型别名。它不能通用表达“基类型 ℕ 且 n>0”这种类型加谓词的约束；`ℕ+` alias 或其他表面写法可能不被识别。把“正整数”静默改成 ℕ 会丢失条件，把它当作 subtype 又涉及 binder 与证明义务，不能只做字符串映射。
3. `Induction` 结构能表达简单自然数归纳的变量、基例、IH、后继步和结论；它不是强归纳、良基归纳或一般递归 case schema。缺少显式结构时的检测含中文词面启发式，不能作为跨语言、跨表述的保证。
4. Definition、scope、assumption 与步骤依赖有结构检查，但自然语言的量词顺序、局部假设的来源，以及 claim/text 与 formal AST 的语义等价没有通用对照器。当前有限 AST operator/type checker 也不等于通用数学类型系统。
5. `sourceMap` 与 diagnostics 的精度目前是步骤/文本块级；没有字符到笔画级证据时，不应展示成原图字符精确定位。

| 数学结构 | 当前可确定支持 | 部分表达/风险 | 当前不覆盖或失败证据 |
|---|---|---|---|

| 多路线证明 | 单一路线 DAG 有 sourceRefs、dependsOn、局部 context，逐步 obligation 和 aggregate 锁定 | 原文可含多种“法一/法二”，但当前将所有 proofSteps 都纳入同一 aggregate 要求 | 无 alternatives/route grouping；即使选用路线通过，另一条错误/未写 proof 的路线仍可令 aggregate 缺失 |

## 建议的架构设计（本轮不接入正式 App）

### 阶段一：只读忠实性证据账本

在现有 MathIR 外建立研究/诊断输出，不改变正式 schema、定理生成和 Kernel 输入。对每个变量域、定义、题设、步骤、局部假设、结论汇总：来源原文版本与 block/span、raw/normalized 对应关系、对应 MathIR node/AST、当前 ambiguity、sourceRef 覆盖情况、检查方法和未判定原因。输出应允许 `supported / contradicted / uncovered / ambiguous / not_assessed` 等证据状态，明确这些状态不是证明结论，也不构成新的产品 Gate。

先做确定性可核查部分：Unicode 范围/来源存在、片段覆盖、节点到 AST 的引用完整性、MathIR AST 到 canonical Lean 的往返/哈希稳定性、量词和 binder 的结构差异。对自然语言与公式的语义等价，当前没有可信通用判定器，应标作未评估，不能让模型自我声称已证明忠实。

### 阶段二：经确认后扩展数学概念表达

候选契约应统一为显式 typed symbol/declaration 节点，而不是继续在自由文本 `domain`、独立 `definitions` 和公式 AST 之间隐含绑定关系。每个变量/常量/定义至少需能指明：类型表达式、定义值或谓词约束、量词/作用域、来源证据、与自然语言名字的绑定。例：正整数可表示为 `n : ℕ` 与 `0 < n` 的题设约束，或确切的 positive subtype；两者的 Lean binder、导出 statement 与证明责任不同，不能由 renderer 猜选。多项式对象需声明 `P : Polynomial ℝ`，自变量 `x : ℝ` 并把 `eval x P` 联系到命题；未出现在表达式里的“展示性名称”不应默默变成 theorem 参数。

证明层需要独立于数学命题 AST：显式 case/induction 节点引用变元、基例、局部 IH、step case 和结论；证明路线节点支持顺序依赖与备选分支。这样避免把 IH 建模为外部定理前提，也避免把题目中“法一/法二”全部误当成必须同时证明的序列。通用量词和作用域应对每个表达式做 typed binding 检查，并保持原节点来源。

每个新字段要定义缺省兼容、旧记录迁移、canonical binder/statement hash 规则和 Lean encoding。不得通过某一道中文题、某种措辞或某个模型输出进行特判。

### 阶段三：分开“结构可编译”与“来源已对照”状态

保留当前 Kernel 的可信边界：它只检查锁定的 Lean statement/proof。API/SwiftUI 若要显示原文忠实性，应消费独立、可追溯的来源对照证据；不能仅将 `kernelVerified=true` 映射成“原文已验证”。是否让 `/api/structure` 对没有 formal 的草稿返回成功、是否新增正式对照状态、歧义怎样参与产品状态，都会改变 API/schema/成功语义，需用户确认后再实施。

## 风险与决策点

- 从原文到 MathIR 的通用数学语义等价目前无法由 Statement Lock、类型检查或 Kernel 自动保证。
- 来源 span 能证明“引用了哪里”，不能证明“该处真的支持此断言”；要解决后者需要新的证据算法或人工核对设计。
- 加入对象类型+域谓词会影响量词、Binder Map、Lean 定理签名和旧 MathIR 迁移；需先确定表达契约。
- 归纳 schema 泛化会影响 obligation 生成、局部假设作用域和 repair 输入；需以不同归纳原则的未参与设计样例验证后再定。
- 从 `formal` 可选改成必需或反之，会改变 `/api/structure` 行为与客户端状态，必须作为 API 变更审议。
- 目前没有证据支持扩充 AI 自评循环、自动补前提或让 Kernel 对原文背书；这些不应由本研究引入。

## 推进优先级

| 顺序 | 工作 | 依据与收益 | 是否改正式契约 |
|---|---|---|---|
| P0 | 保存 source block/raw/normalized/ambiguity 与每个 typed AST 节点、声明、作用域之间的只读证据账本；让报告明确 `not_assessed` | 已有原型对 3 份录制 MathIR 检出 0 个无效 ref，但 6–19 个未决歧义且无 typed formal；coverage 仅说明文本位置有引用 | 否；研究/诊断产物，不参与通过状态。当前只实现开发研究脚本 |
| P1 | 设计声明与类型节点：基类型、域谓词、定义签名/值、量词绑定、局部作用域和来源一体化；增加带类型的数值 literal 与有限区间求和 | 正整数、实角、`P : Polynomial ℝ`、整系数辅助多项式目前不能由 typed MathIR 一致表达；新几何级数 AST 中 `1/2` 默认成 Nat 除法 | 是；需批准 schema、迁移与 Lean encoding |
| P1 | 泛化 induction case 为起点/前提受限的归纳，并将 proof route/cases 与 statement AST 分离 | 新样本需从 n=1 对正整数归纳，当前 validator 要 P(0)；录制证明页也有法1/法2备选路线 | 是；需批准旧 proofSteps 兼容映射和汇总语义 |
| P2 | 扩展表达式静态语义与类型检查，明确有限 AST 的能力边界；形式化前产生可读的未绑定/未覆盖/类型不确定证据 | `formal` 必须齐全且 typed，但自由 claim text、definition text 与 AST 的语义关系仍无确定性保证 | 部分是；AST/operators/API 状态需确认 |
| P2 | 兼容迁移与现有锁定记录重放工具 | 多个重要真实 fixture 属于旧 MathIR（无 formal）；当前 `canonical_plan` 无法从旧的 free text 安全恢复等价 typed AST | 是；需定义只读旧档案与重新结构化的边界 |

统一根因是 MathIR 当前把“源文本、对象类型/定义、公式 AST、证明步骤图”分别保存，却缺少跨层可验证的绑定关系。建议以“带来源证据的 typed declarations + statement AST + proof-route graph”为目标模型；来源对照作为平行证据层，不宣称 Kernel 可证明自然语言等价。该模型一次性处理正整数约束、多项式类型、局部假设/归纳和备选证明路线，优先于对单个 domain alias 或中文措辞打补丁。

### 建议的待确认契约

为了让后续确认有具体对象，建议目标结构概念上表达为：

```json
{
  "declarations": [{
    "id": "n",
    "kind": "variable",
    "type": {"kind": "nat"},
    "constraints": [{"relation": "gt", "left": {"symbol": "n"}, "right": {"number": "0"}}],
    "sourceRefs": [{"blockId": "...", "start": 0, "end": 20}],
    "resolution": "source_supported"
  }],
  "statement": {"...": "typed expression tree"},
  "proofRoutes": [{
    "id": "route-method-2",
    "cases": [{"kind": "induction", "variableId": "n", "baseCaseId": "...",
      "hypothesisId": "...", "stepCaseId": "...", "conclusionId": "..."}],
    "nodes": [{"id": "...", "dependsOn": [], "sourceRefs": []}]
  }]
}
```

这是概念草图，不是要求照此字段命名。建议用户决策如下：

1. **带条件的域：建议 MathIR 保留基类型 + 明确约束。** 正整数写成 `n : ℕ` 与 `0 < n`，Lean statement 可忠实输出为 `∀ n : ℕ, 0 < n → goal`。这样不把正性藏在 subtype，也不把它静默丢掉；若原文没有说明 θ 的类型，则标为未定，不从三角函数场景擅自补成 ℝ。只有题面明确指定 subtype 或用户选定编码时才采用 subtype。
2. **多项式：建议对象类型和求值变量分开绑定。** 例如 `P : Polynomial ℝ`、`θ : ℝ`，statement 明确写 `eval (cos θ) P`。若原文只说“多项式”而没有指定系数域，必须把系数域歧义留在来源证据中；不能由 proof provider 的 notes 决定。定义层再通过 typed value/等式连接命名对象与多项式表达式。
3. **多种证明方法：建议每条原文路线成为独立 proof route。** 路线内部仍按依赖图/局部 scope 组织，归纳结构绑定基例、IH、后继 case 与总结。各路线独立给出步骤与 Kernel 结果；建议总命题在任一完整的用户原文路线通过 Kernel 时可显示“有一条原证明路线通过”，同时保留其他失败路线结果。这个汇总规则会改变现有“全部 proofSteps 均需 proof”行为，需用户明确批准。
4. **旧 1.0 记录：建议只读保留，不反推 typed AST。** 老记录仍展示原文、来源、历史结果，但状态标作 `legacy_untyped`；如未来允许重结构化，应从保存的源材料建立新的 MathIR 版本并链接原记录，不覆盖旧 statement/hash/proof。旧 Lean 类型文本不能转换成 source-faithful AST。
5. **API 成功语义：建议区分 `mathIRStructurallyValid`、`canonicalStatementLocked` 和 `sourceAlignment`。** 第一个只表示 schema/scope/range 等确定性结构校验，第二个表示 AST 成功编译并锁定，第三个是独立的来源证据状态。它们不是新的阻断 Gate；若 structure API 目前必须产出可锁定 statement，则可以先保留这个运行行为，只增加研究账本，不公开“部分成功”。公开新字段/状态仍需确认。

### 目标架构与迁移边界

建议把 MathIR v2 拆成四个互相关联、但判定责任分离的层：

1. **Source Evidence**：保留原始输入、raw/normalized transcript、source blocks、图像页与 bbox、用户修改版本及 unresolved ambiguity。每个数学节点指向一个或多个 evidence spans，并记录 `supported / ambiguous / contradicted / uncovered / not_assessed` 的来源核对状态。这个状态只报告证据，不参与 Lean/Kernel 判定。
2. **Typed Mathematics**：声明对象的 sort/type、作用域、定义签名/值、域约束和来源链接；AST 只表达逻辑/数学内容。数字 literal 必须能明确为 Nat、Int、Rat、Real 或多项式系数域；有限和表达上下界和端点约定；量词 binder 明确作用域。正整数以 Nat + positivity constraint 表达时，canonical compiler 固定生成 `∀ n : ℕ, 0 < n → ...`。多项式声明如 `P : Polynomial ℝ`，求值为 `eval (cos θ) P`。禁止由字符串名或 proof response 隐式改类型。
3. **Proof Routes**：原文中的每条方法成为独立 route；route 内含 step DAG、局部 hypothesis scope、lemma dependency 与 induction/case node。Induction node 需记录 principle、变量、起点/基例、IH 断言、step 条件/结论和总目标，能表示从 1 起步的正整数归纳；强归纳、列表/树递归等使用不同 case schema，而非把 IH 塞成 theorem assumption。
4. **Formalization/Verification**：deterministic compiler 从 typed statement 派生 Binder Map、canonical statement 与 Statement Hash；每条 route 单独生成 obligations 和 Lean proof。Lean 编译、诊断修复和 independent Kernel 仍沿用当前可信边界。建议 hashes 分别标识 source evidence、typed statement、proof route；proof/route/source 更新不能静默变动 statement hash，statement 变化则重新锁定并重建验证记录。

对多条路线的用户可见总状态，建议逐路线保留通过/失败，并将“至少一条完整用户路线 Kernel 通过”作为存在性成功；但这属于当前 aggregate 语义变化，必须确认后才能实施。若目标是要求所有原稿路线都正确，则 aggregate 应保持 all-of。系统不能自动删去失败路线或用 AI 新 proof 替代原路线。

兼容方面建议：旧 MathIR 1.0 与旧 hash/proof/certificate 原样只读保存；没有 typed AST 的旧记录不迁移成新 canonical statement。升级应用后可读取旧展示结果，但不可把旧的模型生成 `FormalTypes` 当成 MathIR v2 source of truth。若之后确认重结构化旧源，创建带 `supersedes/derivedFrom` 关系的新记录，保留旧记录和 hash。v2 API 以独立版本字段/endpoint schema发布；老客户端继续消费 1.0，避免把 `formal` optional 的历史草稿误读为 statement locked。

语义忠实性没有一个普适的确定性算法可以将中文/手写自然语言证明等价转成 Lean。v2 的目标是让模型解释显式、可追溯和可反驳：分不清的类型、系数域、量词范围或笔迹留为 `ambiguous/not_assessed`，固定 theorem 与 source evidence 分开显示；这不改变 Kernel 的权威，也不把 AI 的“忠实”自评当作数学证明。
