# Mathlib 候选证据组织 V6 最终对照与架构决策

基线为 `daa499a`。本轮复用 V5 固定请求计划和真实来源 fixture，向 DeepSeek `deepseek-flash` 发送 **9 次**请求：主等式 A/B/C+ 各一次，代数和三角样本各 A/B/C+ 一次。没有重试、没有重复 input hash，也没有修改正式 Prompt、Retriever、候选集合、MathIR、Statement Lock、Lean/Kernel、客户端或正式 App。

## 付费前核对与同条件范围

运行器从 V5 fixture 和构建器重新生成所有最终 HTTP body，并与磁盘中保存的 request body、input hash 逐字节核对。9 份请求都通过：DeepSeek 模型为当时服务端配置的 `deepseek-flash`，system Prompt、schema、每个样本的固定 MathIR/命题/diagnostics/步骤顺序相同；每个三方案组只有 `mathlib_candidates` 的表示不同。主样本 statement hash 为 `b603da078a203eb54e721b482057091de175a3ded724a549b56a374a73677ca3`，代数为 `e83039e82bfe545e2bad30e0f4f2dd44bcf66f6ceba462fdc0e92b1b379769f7`，三角为 `bdb9b397e0e62bd12506bc06990fbdb938bf82d04f2727390cd8c6285fcc12ea`。

主等式 A 确为历史 retrieval：302 个候选声明、288 条来源记录；来源路径、文件 SHA-256、模块、声明行和源码头均与本机 Mathlib 4.34.0 相符。B 仅在模型提示中移除来源行和引用，A 与 C+ 的 288 条来源数据及候选映射相同，C+ 可逐字段无损解码回 A。三方案都保留同样的 302 行、296 个真实 `#check` 签名及 found 状态。

代数和三角样本的 A/C+ 来源来自**本机按已存档 query 在 Mathlib 4.34.0 上重新检索**，不是旧存档 retrieval。旧存档的 sourceMatches 都是 0；本机重建分别为 76 个候选/74 条来源和 38 个候选/34 条来源。B 不含模型可见来源。归纳样本不发送：存档 MathIR 缺少显式归纳结构，被当前 Compiler 以 `IR_INDUCTION_STRUCTURE` 拒绝；本研究没有改写其 MathIR。

全部请求先写入 SQLite ledger，再发送；响应和 usage 收到后立即落盘，然后做本地检查。9 项最终均进入 ledger，状态为已验证或响应已验证但模型响应不完整。HTTP 库不重试，所有 retry index 为 0；研究端 cache 全部 miss。每个 response 的 reasoning token 数保留，但 Provider 私有 `reasoning_content` 未复制进结果文件。请求 ID、workflow ID、input hash、prompt version、模型、HTTP 时间和 token usage 在 `audit.jsonl`；原始 request body 与响应主体在各 JSON 中，不含 API Key。

总计 552,737 输入、108,201 输出（其中 107,607 为 reasoning）、191,744 个 cache-hit 输入 token、360,993 个 cache-miss 输入 token；HTTP 累计约 370.614 秒。这里只报告 tokens 和 Provider cache 使用量，没有按未核实的价格表换算美元。特别是主等式 A 有 162,944 cached input tokens，B/C+ 各只有 2,432；所以 input-token 数量下降不能直接等同于账单同比下降。

主等式的三份 proof 都逐项在 Lean elaboration 中通过，并由独立新环境 data-only Kernel replay 通过，证书均匹配同一 statement hash，`additionalAxioms=[]`。三份 proof 都按原步骤顺序证明：第一步用 `congrArg` 将原等式加一，目标引用该已通过步骤。历史 V3 A 是另一时间的额外参考（163,160/999 tokens、Kernel 通过），不是本轮同期 A；本轮 A 的 163,160 输入 token与之相同，且 input hash/固定 diagnostics 相同，但它属于不同时间的响应，未将它替代本轮 A。

代数组虽然三个响应都符合 `ProofBodies` JSON schema、statement hash 都正确，但 Lean 结果相同地失败。A 为每个义务在已有局部上下文上再次 `intro`，真实诊断是 `introN failed: There are no additional binders`。B/C+ 返回的若干 proof body 缺少 `by`，Lean 将 `intro` 当作未知命令。该失败说明当前样本的模型输出与 formalization 输入形态没有对齐；它不能证明移除或压缩来源导致能力下降。三个 aggregate 均由 Lean 拒绝。

三角 A 的 `finish_reason=length`，completion/reasoning usage 达到 65,536 token，消息内容为空，无法通过 JSON/schema 验证。依照计划不重发。B/C+ 都只返回并验证既有两个失败义务 `step_take_P`、`goal`；Lean 两步和完整 aggregate 均通过。原有 8 个通过片段保持不变，保存的 proof hashes 与修改前相同，命题 hash 不变。这验证了该 repair 请求的完整数学结果，但不能单独证明 B 或 C+ 优于 A，因为 A 没有可验证输出。

逐 proof 批量 Lean elaboration 与独立 aggregate Kernel 的实测时间如下。批量阶段为同一个隔离 Lean 进程中的独立 theorem declarations，错误诊断按各 theorem 行区间映射；aggregate 阶段使用现有 runner，在新环境进行数据式 Kernel replay。

三角 B 和 C+ 两个模型输出的 proof body 完全相同：`by rfl` 与 `by use ((4 * (Polynomial.X ^ 3)) - (3 * Polynomial.X))`；两者均保留原有八个已通过片段。这说明本样例观察不到 B/C+ 对生成文本的差异，并不能证明模型读取或使用了 C+ 来源索引。

V6 使用固定顺序 A→B→C+，同一组三次请求不是并行请求；Provider cache 命中在各请求之间不同。即使输入条件受控，模型也可能非确定。V4 同 hash 的 B 两次真实响应曾一失败一通过；V6 没有为测方差而重复任何调用。

## A、B、C+ 的风险与解释

**A 全量**保留完整、直接可读的来源对象，模型不需解释索引格式。它在主等式这次成功，也有 V3 历史通过记录；但三角 A 在本轮实际生成超长 reasoning 并截断，说明全量上下文也可能触发代价很高的失败。不能称 A 的成功率已被证明最高。

**B 名称与签名**在三个样本都保留全部候选、found 状态与真实 `#check` 签名。它确实最省输入 token（本轮各自比 A 少 36–48%），主等式和三角 Kernel 均通过。它让模型失去 288/74/34 条词法源码命中的 sourceName、模块、文件、hash、行号、声明头及候选到来源的引用；服务器端完整 retrieval 仍保留。V6 样本数不足以证明这些信息对未来任务无用，故 B 的成本优势与来源可解释性损失都应保留在风险评估中。

**C+ 可逆来源索引**保留完整来源行，V6 每个样本都通过固定 statement 的 proof/Kernel 验证（代数与全方案共同失败，三角 A 截断）。主等式实际输入比 A 少 12.4%，代数少 9.8%，三角少 11.5%；比 B 消耗更多输入 token。它没有在本轮输出中引用来源路径或行，proof-only schema 也不要求输出证据引用；因此不能据“proof 通过”断言模型正确解析或使用了 `sourceFiles/sourceTextTables/sourceMatchRows`。目前 prompt hash 与 A/B 完全相同，没有加入 C+ 解码说明，这是严格控制只变证据表示的结果，也留下了索引理解风险。

所有 Kernel 通过只证明 Lean 接受对应固定 theorem；自然语言步骤与 Lean obligation 的语义对应仍依赖 MathIR/Statement Lock 和已有来源映射。它不会证明关键词搜索命中在数学语义上相关，也不会让 AI 对原稿的解释自动成为定理。V6 没有改 Kernel 信任边界。

## 最终架构决策

**建议保留现有 A，暂不将 B 或 C+ 接入正式 Prompt。** 这是依据用户给定的“证据不足时保留 A”的决策，不是声称 A 已被统计证明为成功率最高：

1. 三方案在主等式均 Kernel 通过，无法以结果区分。
2. 代数三方案均因 proof body/局部上下文格式不匹配而失败，无法判断来源证据影响。
3. 三角 B/C+ 通过，但 A 输出被截断；这是成本和可靠性信号，却不是同条件成功率胜负。
4. B 有最大实测 token 降幅，但会删除全部模型可见来源信息；当前样本不足以排除这些线索对别的证明有帮助。
5. C+ 保留信息但只减少约 10–12% live input tokens；模型是否能使用其索引还未被输出证据验证，复杂度与收益暂不相称。

所以当前生产选择是 A。C+ 可保留为可复现的研究工具，不开 V7、不自动发更多请求，也不做正式产品替换。若后续经确认要考虑替换，先在离线构造中显式定义索引 schema 与模型可理解的映射说明，再以固定请求、durable ledger、逐 proof Lean、aggregate fresh Kernel 和现有完整 retrieval 进行回归；这属于未来实施前的必要设计，不是本轮生产改动。
