# Mathlib 候选证据架构与离线实验 V5

基线为 `0fff867`。本轮没有发送 DeepSeek 请求，没有修改正式 Prompt、Mathlib retriever、候选范围、DeepSeek Provider、MathIR、Statement Lock、Lean/Kernel 或 App。研究实现位于 `devtools/research/mathlib_candidate_evidence/`；所有 request body 均标为 `planned_not_sent`。

V4 的有效来源证据 A/B/C 样本数仍是 **0**。本报告不把它改写成成功的模型对照，也不声称 C+ 的模型证明能力已经胜过 A 或 B。

## 主要输入：原始 V3 等式记录

主 fixture `fixtures/equation_v3_302_288.json` 从保存的历史 SQLite artifact 导出，完整保留原 retrieval、MathIR、形式化记录、repair diagnostics、历史模型结果和 Lean/Kernel 结果。来源是原始保存数据，不是本机重建。

- retrieval 有 **302 个 declaration rows、288 个 source matches**；296 个找到的声明有 296 个非空且唯一的真实 `#check` signature。
- 所有 288 个 source match 均能映射到相同名称的候选声明；无无效索引、未引用来源行或缺失候选名。
- 从固定命题、proof obligations、旧 proof、diagnostics 和 A 候选上下文重建出的输入 hash 是 `8979f0b618e30b50bd961d362ce24ad99c17018893e23ef69dc0fa33ef563857`，与历史 A audit 完全一致。这个命中证明历史 A 输入可复现。
- 历史 A 的 DeepSeek usage 为 **163,160 输入 token、999 输出 token、961 reasoning token**；两段返回 proof 共 69 个字符 / 69 字节。历史 A 的保存结果经过 Lean Kernel 验证通过。旧审计把 stage 记成 `formalization`；从 payload 的 diagnostics 可确定其语义阶段是 repair。

复现 fixture 和 request 的具体字段、artifact IDs、来源说明都保存在 JSON 中，避免只依靠这份摘要。

## C+ 编码和请求输入自检

C+ 保持候选声明行不变，并把来源按索引编码。`sourceFiles` 去重保存 module、相对路径和 source SHA-256；五个文本表分别去重 `sourceName`、namespace、`declarationLine`、`declarationHeader` 和 evidence 标记。每条 source row 用候选索引、文件索引、行号及文本表索引表示。每个 declaration 仍保留指向来源行的引用。源数据没有丢弃，`decode_c_plus` 能逐字段还原为 A 的完整 prompt evidence。

离线自检通过的事项：

- A/B/C+ 保留相同的 **302 个候选行、found 状态、296 个真实 signature 及诊断字段**。
- C+ 反解结果与 A 完全相等；A/B/C+ 所有来源引用均有效，288 行均有对应候选。
- 三个请求的 MathIR、statement hash、repair proof、diagnostics、obligations、prompt、schema、model 和其他 payload 字段相同，只有 `mathlib_candidates` 的组织方式变化。
- 三种证据 hash 与 DeepSeek input hash 均各不相同。A hash 与历史审计相同。
- 保存的最终 Chat Completions JSON body 不含 Authorization header 或 API key；每个 request plan 都明确标注 `planned_not_sent`。

| 方案 | 证据 UTF-8 字节 | 相对 A | planned input hash |
|---|---:|---:|---|
| A 全量 | 406,344 | 100% | `8979f0b618e30b50bd961d362ce24ad99c17018893e23ef69dc0fa33ef563857` |
| B 全部名称和签名，去掉来源行 | 194,577 | 47.9% | `455b65bed42f80695f5a00b4559d0e3861f1aea36e3fc44f6456a9eb6cabb2e6` |
| C+ 可逆来源索引 | 333,964 | 82.2% | `e9c25772bf93bacad046fb153ee513861aef2ff078d88d6e07d5c23964fac246` |

C+ 比 A 少 **72,380 字节（17.8%）**，比 B 多保留来源行、文件位置、hash 和声明头。B 少 **211,767 字节（52.1%）**，但模型看不到这些来源信息。字节不是 tokenizer token 数；本轮没有把它转换成估算 token。

三个实际最终 request body、prompt/schema/version/input hash/body hash 都保存于 `generated/requests/{A_full,B_names_checks_only,C_plus_lossless_index}.json`，索引在同目录 `manifest.json`。A 有历史 token usage；B 和 C+ 都未发送，token、推理用量和 proof 输出均未知。

## 其余样例：原存档与本机重建分开

样例 fixture 将当时保存的 retrieval 原样留在 `savedRetrieval`。本机重建另写入 `reconstructedRetrieval`，来源是同一存档 query 在本机 Mathlib 4.34.0 源码上的 `LibrarySearch.search_many`，再用一次批处理 Lean `#check` 核对所有候选名。它们不是原始历史 retrieval，也不会覆盖原样例。

| 样例 | 原存档 declaration/source rows | 本机重建 candidates/source rows | saved signature 与新 `#check` 差异 | C+ round-trip |
|---|---:|---:|---:|---|
| 代数 | 4 / 0 | 76（72 found）/ 74 | 0 | 通过 |
| 归纳 | 4 / 0 | 84（84 found）/ 81 | 0 | 通过 |
| 三角多项式 | 10 / 0 | 38（38 found）/ 34 | 0 | 通过 |

这三组 C+ 尺寸是对重建来源的离线结构测量：代数 98,869 → 82,278 字节（16.8%）；归纳 93,163 → 75,584 字节（18.9%）；三角多项式 36,645 → 28,324 字节（22.7%）。B 分别是 48,419、40,628、17,163 字节。它们不是对原始存档来源的压缩结论，因为原存档的来源行数都是 0。

归纳失败样例里的旧 MathIR 含全局 `step_ih`，缺少显式 induction structure；当前 Compiler 以 `IR_INDUCTION_STRUCTURE` 拒绝它。我没有为了生成 request 而重写 MathIR。归纳样例保留在来源索引、可逆编码和 signature 核对中，但当前不生成 repair request plan。其排除原因已写入 cross-sample request manifest。代数生成了 formalization 计划，三角生成了针对现有 `step_take_P` 与 `goal` diagnostics 的 repair 计划；两者都只保存最终请求结构，未调用 Provider。

同一 B input hash 的两次输出，一个未通过、一个通过，proof 长度也明显不同。这是直接的非确定性生成波动证据；因为这组输入没有源码行，不能把 C 成功解释成 C+ 或来源保留造成的提升。V4 另有一个已中断的重复 C 请求；没有 usage。以上都是历史请求，本轮没有产生新 DeepSeek 调用。

历史大等式 A 的输出 usage 记录了 961 reasoning token；V4 的旧审计文件没有保留逐请求 reasoning-token 细项。本轮新的 B/C+ 计划均无 output/reasoning usage。账本会保存后续响应提供的 usage 原对象，而不从 proof 长度推测 reasoning 用量。

## 可恢复 request ledger

`ledger.py` 为研究 runner 提供 SQLite durable ledger，但自身不连接网络：

1. 先保存最终 request body、body hash、evidence input hash 和版本。
2. 调用方发送前标记 `in_flight`；收到响应后先落盘 response 与 usage，再开始 schema/Lean 验证。
3. 重启时复用 `response_saved` / `validated` 的结果；`in_flight` 转为 `outcome_unknown`，不会自动重复请求。

4 个本地单测通过，覆盖 A/B/C+ 输入自检、C+ 完全 round-trip、已保存 response 的恢复复用，以及未知发送结果不会自动重发。它没有连接正式 Provider，也不形成正式产品 Gate。

## 离线验收结果与建议

可复现结构、哈希、mapping、请求计划、ledger 和 Lean 输出都已落盘。本轮有效来源数据 A/B/C 的 **DeepSeek 样本仍为 0**，因此无法判断 C+ 是否改变模型选证或证明成功率。A 的旧 token usage 可作历史成本参考，不能与尚未发送的 B/C+ 直接做节省率比较。

可供下一轮评审的架构是：完整 retrieval 作为原始记录保存；候选名、found、真实签名原样保留；prompt 中用 C+ 的文件/声明来源索引减少重复字段；不排序截断、不丢弃候选；Lean `#check`、Statement Lock 与 Kernel 信任边界完全不变。C+ 的理由目前是可逆性和实测序列化体积，不是已验证的 AI 能力结果。真正的少量 live A/B 应先复用这些 `planned_not_sent` 请求和 ledger，再由 ChatGPT 审阅后决定是否执行。
