# Mathlib 候选相关性研究 V3

研究基线为 `71f6935205efe6098673c5cb77cc922a6760f639`。本轮只读使用已保存的真实 formalization / retrieval / verification artifacts，以及本机安装的 Mathlib 4.34.0 源码树。没有发送 DeepSeek 请求，没有改正式检索、模型 prompt、候选集合或证明逻辑。机器可读统计在同目录 `mathlib-candidate-relevance-v3/metrics.json`。

## 宽泛查询的实际来源

等式 repair 的八条查询中，`Eq add right` 在当前真实 Mathlib 源码索引上命中 254 个不同声明位置。匹配条件是查询词可分散出现在声明名、文件路径和声明头中；因此 `Eq`、`add`、`right` 的共现不表示声明可用于当前 goal。命中样例包括 `List.prod_mul_prod_eq_prod_zipWith_mul_prod_drop`、`RingCat.Colimits.Relation`、多个 `CategoryTheory` 与几何 `RightAngle` 模块。来源索引的 top module 还包括 `Mathlib.Geometry.Euclidean.Angle.*`，与实数等式加一无关。

把查询改得更像定理名会减少部分噪声，但仍不等于语义相关：`add_right_inj` 命中 11 个位置，`add_left_inj` 命中 22 个，`add_right_cancel_iff` 命中 1 个；但 `Real add` 仍命中 846 个。严格要求所有词同时出现在同一声明名时，`Eq add right` 仍有 133 个。词法重写无法单独给出安全的候选边界。

源码索引还会漏掉已知声明：直接查询 `Finset sum_range_zero` 与 `Real cos_two_mul` 分别返回 0 个源码命中，但对应保存记录中的精确声明名均有真实成功的 `#check` 签名。因此，关键词搜索适合提供来源提示，不能取代模型给出的完整声明名和 Lean `#check`。

## goal、局部类型与真实签名的相关性

保存的真实 proof 和签名展示了有用的类型信号：

- `sub_sq` 的签名要求 `CommRing`，正好支持实数平方差展开；`sq_nonneg` 的签名给出平方非负；`sub_nonneg` 的 iff 形式用于最后一步不等式转换。
- `Finset.sum_range_succ` 的签名将 `range (n+1)` 的和分解为 `range n` 加末项，和归纳步骤及局部 induction hypothesis 对齐；`sum_range_zero` 对应基例。
- `Real.cos_add`、`Real.cos_two_mul`、`Real.sin_two_mul`、`Real.sin_sq_add_cos_sq` 的参数类型均为 `ℝ`；`Polynomial.eval_sub/mul/pow/C/X` 的 `Semiring`/`Ring` 条件适配 `Polynomial ℝ` 的目标。
- 等式样本的已通过 repair 使用 `congrArg (fun x : ℝ => x + 1) h0`。真实 `congrArg` 签名是泛型等式同余，不含 `Real` 或 `add_right` 这些词；它的可用性来自把函数 `x ↦ x+1` 应用于当前局部等式，而不是字符串相似。

我另外离线试了一个明确的弱基线排序器：把 MathIR 原文、目标文本、步骤文本/理由、Binder Map 类型及 Lean expected type 拆成英文标识符；分数为“声明名 token 重叠数 ×3 + 签名 token 重叠数”，同分按名称排序。它只重排存档候选，未过滤生产数据。结果为：

- 等式中实际使用的 `congrArg` 排在 302 项中的第 113 位；top-50 会漏掉它。
- 三角样本 top-5 只覆盖 9 个显式引用中的 4 个；top-10 才覆盖 9/9，但原集合本来只有 10 项，几乎没有缩减。
- 代数候选的上述词面分数全为 0，所谓前三项覆盖只是同分名称顺序，并非相关性证据。
- 归纳样本只有 4 项，排名覆盖不能证明在大集合上可筛选。

所以，“目标/类型 token overlap 后取前 N 项”没有通过多样本留存检查；特别是等式样本给出一个真实反例，足以否定把这类 top-N 当作安全过滤的方案。更强的 Lean expression 形状/类型实例兼容分析值得继续研究，但本轮没有实现或声称验证了它。

## 候选证据组织的旁路成本测量

最大等式样本当前给模型的 `prompt_mathlib_evidence` 在 provider 使用的 `json.dumps(..., ensure_ascii=False)` 格式下为 398,629 字符 / 406,344 UTF-8 字节。另构造了一个**只用于测量**的组织方式：保留同一 302 条 declaration rows、状态和全部真实签名，只从模型提示副本中拿掉 288 条 `sourceMatches` 展开及 `sourceMatchIndices`；完整来源映射仍留在原 retrieval artifact。该副本为 191,218 字符 / 194,725 字节，少 207,411 字符（52.0%）。302 个声明名和签名没有删减；288 个 source-match 名称仍在 declaration rows。

同样的副本变换在代数、归纳、三角样本分别只减少 104、104、260 字符（约 3.6%、4.6%、5.6%），因为这些记录没有 `sourceMatches`。因此这项潜在节省集中在异常膨胀的等式检索记录，不是所有证明的普遍 52%。字符/字节是实测序列化规模；本轮未再次向模型发送精简版请求，所以**没有声称对应的 token 节省或证明成功率**。

这一组织方案不会删除候选名、签名、`found` 状态或服务端原始来源记录，Lean 检查和 Kernel 接受边界也不变；但它会令模型看不到源码路径、行号和源码声明头，模型据此选择/解释声明的能力可能变化。它是证据展示层改动，仍需用同一批样本做批准后的真实模型 A/B，才能判断识别质量是否保持。

## 结论与待确认事项

有真实证据支持的下一步是：保留所有 declaration names、`#check` signatures 和服务端完整来源映射，单独评估不向模型提示展开重复 `sourceMatches`。等式 outlier 的离线文本规模下降约一半，其他三例影响很小。另一个方向是对全部候选按 Lean goal 形状和局部类型做类型兼容排序，但目前简单排序反例明确，必须先实现更强的旁路方法并在四类样本上验证；不应过滤候选或设置 top-N。

本轮没有提交生产代码变更、没有修改候选集合、没有新建 Gate/模型路由，也没有进行新的 DeepSeek 或 Kernel 调用。以上两个方向尚未接入正式业务；尤其来源证据从提示中移除会改变模型可见的支持材料，待用户确认后再开始生产 A/B。
