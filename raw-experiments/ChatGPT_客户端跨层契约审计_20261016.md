## 当前可确认的跨层能力
1. ProofRecord(v2Run:mathIR:) 从持久化 V2 run 构造展示数据；formalType(for:) 读取实际 verification.routes[].steps[].expectedType，不用原文片段伪装 Lean 目标。
2. v2Rows() 按 routeId/nodeId 关联来源节点和验证步骤，读取 sourceRefs、dependsOn、dependencyEvidence、failureClass；展示文案区分 Kernel 已检查与原文语义等价未证实。
3. ProofRecord.verified 对 V2 明确排除 partial、failure 非空、缺失完整 original route Kernel 结果的情况。
4. NativeStore 保留 MATHIR_V2_INVALID 失败草稿，只在匹配来源修订的同一任务读取；V3 值域未决错误展示独立于数学证明失败。
5. NativeV2StructureFailureEvidence.pendingDomainReviews 需要错误码、草稿身份、未验证状态、TypeVar 证据匹配；不将候选数域直接视为用户授权。
6. 最新 cec6ad9 隔离 GUI 证据已验证原生窗口、编辑器、Command-N、导入弹窗和空历史；不等于真实模型到 Kernel 的全链路。

## 需要进一步核实的具体跨层风险（仅观察/待验证，不是已确诊缺陷）
A. BackendClient.swift 的 sourceFragments 使用 blocks.first(where: id)，在来源块 ID 重复时不显式拒绝；且允许 start==end。与 NativeV2StructureFailureEvidence 对重复 ID 和非空范围的严格约束不同。需核实上游正式 MathIR 是否总能保证唯一 ID、非空 SourceRef，以及历史损坏记录如何降级；不能仅凭此片段宣称存在实际错判。
B. v2Rows 将原文片段赋给 math/original 两个展示字段；Lean 实际目标经 formalType(for:) 另行获取。需逐屏检查所有 UI 消费方是否始终明确区分原稿文字与形式命题，尤其新扩建的复合对象/多行公式。
C. v2Rows 的逐步 passed 表达依赖 status==passed 与 dependencyEvidence；完整原路线绿色结果另由 verified 检查。需结合后端序列化核对 status 与真实独立 Kernel step certificate 的关系，确保步骤红绿不会被局部状态误解释。
D. NativeSystemError 现显示 V2_TYPE_DOMAIN_UNRESOLVED 的 pending type variables 与候选数域。Codex 扩展到抽象代数结构/参数化类型后，需确认该显示仍准确、不会将候选类型类约束误显示为已确定数域；先对齐实际新契约再实施 UI 修改。
E. 新 MathIR 类型/运算进入客户端时，检查数学排版和长证明步骤的布局、可复制性、原稿来源映射和未支持/未明确类型提示。现有 UI_STATE_MATRIX 的“页面已实现”不能当作新数学对象已被实际渲染。
