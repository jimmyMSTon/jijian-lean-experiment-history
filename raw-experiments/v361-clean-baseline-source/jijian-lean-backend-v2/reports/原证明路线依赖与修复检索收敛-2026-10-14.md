## 本轮确定性根因与修复

复核一份真实 DeepSeek 结构化的多步文本证明时，MathIR 的变量 `a,b,c` 在 theorem 与路线的共同父 scope，前提 `a=b` 位于 goal 子 scope，路线则位于它的兄弟 scope。结构本身明确了数学前提和原证明路线，但有三个后端细节阻断了忠实核验：

1. `typecheck.py` 只接受根 scope 上的 theorem assumption，拒绝了 goal scope 内、且确实位于 locked goal 的祖先链上的 `a=b`。验证现在允许 theorem assumption 位于 goal 的 root-to-goal scope 链；兄弟路线 scope 的局部假设仍会被拒绝为 theorem premise。`compiler.py` 同时按 assumption 自己的 scope 渲染它，保证其绑定变量可见。
2. 路线依赖在 Lean obligation 中的实际 binder 是 `jjdep_<nodeId>`，Proof-only context 却给模型列了 `h_<routeId>_<nodeId>`。第一次真实生成的步骤因此使用了全局等式前提而没有使用原稿显式声明的前序节点，Lean proof 本身通过，但路线依赖审计正确判为未通过。现在 context 名称与 obligation binder 完全一致；Proof-only 契约也明确要求使用该依赖 binder，不得以相同公式的全局前提替代 `dependsOn`。
3. route composer 另要求每个 claim scope 都包含完整 theorem scope 的 ancestry，因而拒绝了上述合法兄弟 scope。现在 composer 依赖已关闭到锁定 theorem context 的每个 obligation、精确 dependency DAG、局部符号逃逸检查及最终 Lean/Kernel 检查；route-local assumption 仍只有与显式 theorem assumption 表达式完全一致时才可作为其依赖证明。

Repair 路径还会在唯一失败为“声明的 dependency 未使用、没有 Lean diagnostics”时生成 Mathlib LibraryPlan。Mathlib 检索不能修正依赖引用，反而把不相关 retrieval 证据加入 Repair prompt。本轮加入按失败证据分类：纯依赖审计失败直接走 proof-only repair，也不向该 repair 带入先前检索记录；只要当前 repair target 有 Lean diagnostics，Mathlib retrieval 仍可正常触发。没有添加调用轮数、Token、题目、模型或全局 Provider Gate。

改动位于：`backend/v2/typecheck.py`、`backend/v2/compiler.py`、`backend/v2/proof_only.py`、`backend/v2/workflow.py`；通用回归位于 `tests/v2/test_structure_pipeline.py` 与 `tests/v2/test_workflow.py`。
