# Mathlib 候选证据组织研究 V4

本轮按用户授权，在临时数据库和本地 Lean 沙盒中进行了小规模 DeepSeek 比较；没有修改正式 Prompt、Provider、retriever、候选选择策略、Lean / Kernel 或 Mac App。研究基于 codex/next 的代码基线 `a7b38fa`。完整请求审计摘要、A/B/C 序列化统计与逐请求结果见同目录 `mathlib-candidate-relevance-v4/metrics.json`；四份实际模型 proof body 在 `mathlib-candidate-relevance-v4/algebra-live-proof-bodies.json`。这些文件不包含 API Key。

## 本轮真正测到了什么

原计划用代数不等式对 A（全量候选上下文）、B（只移除来源展开）和 C（压缩来源表）做严格对照。A、B、C 三个请求使用同一 DeepSeek `deepseek-flash`、同一 ProofBodies schema / prompt、同一 MathIR、statement hash、原证明步骤和本地 retrieval 声明行；只替换 `mathlib_candidates` 的序列化。请求有真实 input/output token、HTTP 时间和 Provider response ID，Lean 使用本机 Mathlib 4.34.0 与 macOS 隔离沙盒。

但隔离实验的样例记录没有保存 `sourceMatches`：三个实际请求的模型上下文里来源匹配数都是 **0**，A 只有空的来源索引字段。因此这次 A/B/C **没有实际比较“带源码来源”与“去重源码来源”**，也没有测到目标等式大样本上预计的 token 节省。输入 token 也印证这一点：三种不同组织方式只在 5,803–5,864 token 间变化。不能把本轮 Lean 结果归因于来源证据的增删。

这一样例仍给出了有限的实测信息：同一个缺少 sourceMatches 的代数上下文下，A 的 proof 未通过 Kernel、B 的 proof 未通过 Lean、C 的 proof 通过 Lean 各步骤及 aggregate Kernel。模型输出差异包含对已在上下文中的变量重复 `intro`；Lean 正确拒绝了不成立的片段。由于上下文缺少来源数据，A/B/C 能力差异可能来自模型生成波动，不能作为方案胜负结论。

## 历史记录与本地来源重建

V3 的等式记录是**历史对照**，不是本轮严格同条件 A/B/C：历史全量 A 请求 `ea83b3f7-651b-4010-9202-c7bf98877d7c` 使用 `deepseek-flash`，输入 / 输出 token 为 163,160 / 999，HTTP 6.809 秒，证明引用 `congrArg` 且 Kernel 通过。它有 302 个候选声明与 288 个源码匹配。V3 中从模型提示移除来源行的序列化副本从 406,344 字节降至 194,725 字节（52.0%），但没有做 live B；不能据此声称 token 降低 52% 或能力不变。

为实际衡量 C 的压缩和来源保真，我另在当前安装的 Mathlib 源码上，用三个既有样例保存的同一批查询做了**离线词法检索重建**，没有调用 Provider，也没有筛候选或设 Top-N。已有 `#check` 声明名、found/signature 保持不变。结果如下，字节为 `prompt_mathlib_evidence` JSON UTF-8 序列化后的研究值：

| 样例 | 候选声明 | 重建来源位置 | A 全量 | B 去掉来源展开 | C 去重文件表 + 声明行 | B / C 相对 A |
|---|---:|---:|---:|---:|---:|---:|
| 代数 | 4 | 74 | 54,482 B | 7,809 B | 18,774 B | −85.7% / −65.5% |
| 归纳 | 4 | 81 | 55,937 B | 7,541 B | 18,070 B | −86.5% / −67.7% |
| 三角多项式 | 10 | 34 | 36,905 B | 19,332 B | 20,395 B | −47.6% / −44.7% |
| 历史大等式 retrieval | 302 | 288 | 396,039 B | 190,639 B | 241,794 B | −51.9% / −38.9% |

C 保存所有候选的名称、found 状态、真实 `#check` 签名，并用一份去重文件表（module、相对路径、source SHA-256）和来源行表（候选名、文件索引、行号）表示每个来源。大等式样例的 C 表有 128 个唯一文件和 288 个来源行。它比 B 多保留了文件及声明位置，较 A 减少约 39% 序列化字节。来源匹配仍是词法搜索，不代表声明与目标数学上相关；精确 `#check` 签名仍是声明存在性的证据，Lean Kernel 仍是 proof 判定者。

这些字节是离线序列化实测值，不等于 DeepSeek tokenizer token 数。本轮三次 live 请求没有来源行，live token 数不能用于验证该表的节省估算。历史 equation A 的 token 量也来自另一请求与不同 diagnostics，不与本轮相减。

## 三种方案比较与建议

A 完整保留当前模型可见的来源对象，信息最直接，但大样例重复展开 file、module、source hash、declaration header 会显著膨胀上下文。历史样例说明膨胀真实存在；本轮未对有来源行的样例完成 A 的有效复测。

B 保留所有声明名、found、签名并移除 sourceMatches 与索引；当前离线字节节省最多。它同时令模型失去文件和行号来源线索。Live B 的失败不能证明这种删减导致能力下降，因为实际 B 输入中本来就没有 sourceMatches。

C 也保留完整候选集及服务器侧 retrieval；在模型提示中把重复源码元数据改成去重文件表与紧凑行映射。离线数据量在三样例与历史大等式上都明显小于 A，同时保留文件、模块、内容 hash 和行号。C 是目前最值得进一步验证的折中架构，但 live 代数 C 成功不是该包装胜出的证据，因为其来源数组为空。

**架构建议（尚未实施）：**保持服务器 retrieval artifact 完整；模型提示采用 C 的来源文件表和行映射，声明名、found、真实签名、错误状态和完整候选集不变；不做排序截断或筛除；来源证据仅辅助模型选择，Lean `#check`、Statement Lock 与 Kernel 的信任边界保持原样。只有在有来源数据的真实 A/B/C 请求、相同 diagnostics 和固定样例上取得可复核结果后，才建议把 C 接入正式 Prompt。B 可作为诊断 ablation，不建议作为默认，因为其完全删除模型可见来源。

## 范围与限制

- 有效的严格 live A/B/C 样本数：**0**（本轮代数请求严格控制了其他输入，但序列化之前来源记录已缺失；这不是来源证据实验）。
- live ProofBodies 变体输出：A、B、C 各 1 个；另有重复 B 1 个。来源增删的能力结论：**不可判定**。
- induction 与 trig：本轮没有新 live 请求；历史 Lean/Kernel 结果只作为样例背景，不能当成 prompt A/B 结果。
- 未执行真实图片识别，也未调用外部 AI 做语义评估；这项研究只针对 Mathlib 候选上下文。
- DeepSeek 的 retry 设置、缓存行为和正式用户路径均未修改；没有新增 Gate、候选限制、模型或 Kernel 例外。
- 没有修改正式 App 或构建 App。工作内容仅是这份研究记录和隔离实验数据。

这轮 live 结果不支持立即选择 A、B 或 C 接入产品。建议采用 C 作为下一轮**研究设计候选**，但先确保 retrieval fixture 确实带有 sourceMatches，并用一组固定 diagnostics 做少量、可复现且结果先持久化的对照；当前报告中的 C 不应被误读为已验证成功。
