# Repair 上下文膨胀与成本优化 V2

## 调查对象与原始成本

调查的真实 job 为 `28b320e9-660b-424a-a302-67460ad6aae9`，工作流 `99c6b8bc-39d5-48c8-af21-731972fadd48`。从本机真实 `ai-audit.jsonl` 按 `request_id` 去重后，原流程是 9 次 DeepSeek 请求：MathIR 1、formalization 1、repair 4、Mathlib LibraryPlan 3（审计 stage `other`）。合计输入 407,018 tokens、输出 36,130 tokens，Provider HTTP 用时 160.808 秒；所有请求 retry index 为 0。

四次 repair 请求的输入分别为 162,026、162,158、33,250、33,445 tokens，合计 390,879 tokens。前两次输出 6,649 和 8,675 tokens，HTTP 用时 31.303 和 39.539 秒；后两次输出 883 和 741 tokens，用时 4.099 和 4.319 秒。

## 已证实的根因

每一轮 repair 先对同一组未通过步骤执行一次 Mathlib retrieval，然后 `FormalizationService.repair` 按步骤分别调用 `ProofBody`。因此同一轮中，两个不同步骤各自重复传输了完整的 `mathlib_candidates`。两次请求的 proof、Lean goal、局部上下文和 diagnostics 不同，整条请求的 `input_hash` 也不同；重复的是同一份大型检索证据，不是完全相同的 repair 请求。

第一轮的模型可见 Mathlib evidence 序列化为 388,324 个字符，分别传给两个步骤；对应两次请求共消耗 324,184 输入 tokens。第二轮 evidence 为 75,642 个字符，同样传给两个步骤，共消耗 66,695 输入 tokens。没有发现 declaration 名称或签名在各自 retrieval 结果中重复。retriever 会把候选名称合并后一次执行批量 Lean `#check`；不是每个名称重复启动一次 Lean。

第一轮 302 条声明、288 条源码候选的主要来源已经定位：模型生成的宽泛关键词查询 `Eq add right` 单独匹配 254 条源码候选，其中包含与当前等式步骤无关的声明。词法源码命中本身不是 Lean 声明重复或 proof 重复。为了不改变模型可见候选范围，本轮没有过滤这些结果。候选集合收窄的决定仍待用户确认。

两轮 diagnostics 不同：第一轮报告重复 `introN`，修复证明前缀后仍有 Lean 问题；第二轮得到新的 Lean diagnostics。工作流也会对完整 repair input 做 hash 去重。没有证据表明这四次 `ProofBody` 请求是 SDK 重试或网络重试；provider 的实现不做传输重试，四次 `retry_index` 都为 0。两次 `LibraryPlan` repair 请求各对应一轮新 diagnostics，返回的检索上下文也不同；不能把它们认定为相同输入的冗余重试。

同一 Mathlib 查询在本机已安装的版本目录上复测，8 个 query 命中 288 个独立源码位置。`LibrarySearch` 首次扫描及搜索耗时 22.060 秒，已暖缓存再次执行相同搜索为 1.587 秒；结果完全相同。使用实际安装的 Lean 4.34.0 对该记录的 302 个 declaration names 做一次批量 `#check` 耗时 15.556 秒，其中 296 个可解析、6 个未找到。这个 `#check` 是本次本地性能复测，不访问 AI；保存的历史 retrieval 仍保持不变。

## 修复

`FormalizationService.repair` 现在把本轮所有待修步骤按后端固定顺序放进单个 `ProofBodies` 请求。每项仍保留独立的 sourceId、fixed statement、current proof、Lean goal、local context 和 Lean diagnostics；共享的 statement hash、binder map 和完整 Mathlib evidence 只传一次。返回数组长度和步骤顺序经过校验，每个 body 单独通过现有 proof-only validator。Mathlib 候选、Lean `#check`、Statement Lock、Binder Map、逐步验证、成功前缀保护和 Kernel 审计均未改变。没有增加 repair 次数限制。

真实请求审计分类也已更新：包含按 obligation 嵌套 diagnostics 的 `ProofBodies` 请求现在正确计入 `repair`。测试不会使用 fixture 替换真实 provider；fixture/stub 只在明确的本地单元及 wiring 测试中使用。
