### N02：调用增长来自工作流循环与证据累积，不是网络 retry

历史 N02 审计数据包含 41 次真实请求：`mathir=1`、`formalization=1`、`repair=21`、`other/LibraryPlan=18`；输入 `6,231,817` tokens、输出 `177,902` tokens，墙钟 `1,876.834` 秒。40 次收到响应，最后一项失败/中断。41 个请求的 `retry_index` 全为 0，input hash 也全部不同，因此这不是 SDK/网络重试，也不是相同请求 hash 的重复发送。请求增长来自工作流每次 Repair 继续发 LibraryPlan/Repair，输入还带上不断累积的检索上下文；换了 proof 文本或 retrieval 内容也让 payload hash 变化，但没有证明状态改善。旧结果没有可用的 Lean 子进程总数，本文不推算该数。

修复位于 `backend/v2/workflow.py`、`backend/v2/proof_only.py` 和 `backend/library.py` 相关职责边界：

- 先检查已存在 proof；缺 proof 时直接发 proof-only 生成，然后交 Lean/Kernel。不会为尚无 Lean 失败信息的简单证明先请求 Mathlib LibraryPlan。
- Lean 产生实际失败后，先尝试由当前 diagnostics 支持的确定性 proof-only cleanup，并重新执行 Lean/Kernel；只有不能确定性修复时才检索和请求 AI Repair。
- 完整 Mathlib retrieval 记录仍然归档。新增 `mathlibRetrievalScopes`，每份检索结果关联当时的锁定 obligation（route、node、expected type）和 verification-state hash。Repair Prompt 只获取与当前失败 obligation 对应的历史检索证据；相同证据确定性去重，不按候选数量截断，也不丢弃被认定相关的独立结果。
- Repair 停滞判断基于固定 statement/结构 hash、编译出的 obligation、步骤和依赖状态、稳定 Lean diagnostics、Kernel 状态与依赖使用，而非完整请求 payload hash。proof 文本变化、诊断行列偏移或同一通过步骤证书的 proof hash 变化，不会伪装成数学进展。完整原始诊断和每次结果仍保存在 history/checkpoint。
- 一旦再次遇到相同的实质验证状态且没有新增可操作证据，工作流以 `repair_stalled_without_new_verification_evidence` 结束，保存 incomplete 结果和停滞事件。该退出基于已重复的状态，不是固定轮数、Token、难度或 live 开关。

回归覆盖 proof-first、无需初始检索、变化的 proof 文本但相同 Lean 状态停滞、确有新 diagnostics 时继续、确定性 cleanup 先于 retrieval、完整检索历史保留且 Repair Prompt 只选相关 obligation 等行为。历史 N02 未用相同输入和真实模型重跑，因此没有同条件的前后调用/Token百分比；当前改善由通用测试和代码路径证明，不冒充真实 N02 实测节省。

### 单 claim 自由变量 binder 丢失

第一次新鲜 Lean smoke 使用真实 DeepSeek MathIR 与 `rfl` proof。MathIR 锁定 statement 是 `∀ n : ℕ, n = n`，步骤自身 proof `rfl` 可证局部等式，但通用单 claim composer 早退并把裸 `rfl` 当作整个 theorem proof，Lean 报告它的类型为 `?m = ?m`，目标却是全称命题。根因是编译器对单节点 proof 的 trivial shortcut 绕过了 theorem binder composition。

`backend/v2/compiler.py` 已移除该捷径；单节点 route 也走统一 composer，将自由 theorem binders 关闭后再验证。新增通用回归覆盖 theorem root binder，不针对某一道题硬编码。相同已保存 MathIR 与真实 DeepSeek `rfl` 由当前 `complete_and_verify_proof_routes` 重放成功：完整原路线、固定命题和独立 Kernel 均通过，Provider 0 次、Retriever 0 次。真实 Lean Runtime 为 macOS 隔离运行，3 个 Lean 子进程组，总计 `70.764` 秒；独立 Kernel replay 为 `13.47` 秒。机器证据见 `mathir-v2-full-chain-live-workflow-replay-20261012.json`。`semanticAlignmentKernelProven` 仍为 false，所以这证明的是锁定 Typed MathIR 与原 route closure，不是 Kernel 自动证明了中文原文与命题同义。

## 基础模块与剩余边界

现有可靠基础包括严格 Pydantic/Typed MathIR schema、确定性作用域和类型校验、Statement Lock/ProofLock/Binder Map/hash、proof-only patch 契约、sourceRefs/路线依赖图、真实 Lean diagnostics、源码指纹锁定的隔离 Runtime、proof-wire 导出、独立数据式 Kernel replay、axiom/依赖使用审计，以及 fixed statement 与完整原路线分开的成功状态。归纳修复（`5a54fd7`）、Runtime/Runner 协议（`4e8e36a`）、Native V2 展示（`326c7df`、`3226c30`）都进入统一主线。

MathIR `ExprOp` 仍是封闭表达式 DSL，覆盖自然数、整数、有理数、实数、多项式及常用算术/逻辑、量词、有限和、三角函数、求值与 cast；它不直接承载任意高阶函数、任意集合/序列/数学对象或一般函数应用。复杂数学必须能忠实降到现有 AST。类型与 scope 合法不等于自然语言/手写原稿语义已证；当前来源定位粒度也不是图像字符级。Mathlib 候选和 proof-only/Repair 能力仍受实际模型输出、Lean elaboration、局部假设和路线依赖制约。

仍需显式关注的已观察问题：

1. 新鲜 smoke 的 MathIR 失败责任在 `backend/v2/structure.py` 及其上游结构化响应契约：未知 binder 被确定性校验拒绝。下一步应在新的、不同输入的样本中复核模型对已有 binder 声明的引用格式；不放宽 scope 校验。
2. N02 的 Repair 收敛责任在 `backend/v2/workflow.py`；本轮已增加实质状态去重和 evidence scope。历史 N02 没有同条件修复后 live 对照；若后续需要量化实际节省，应在新鲜且完整审计的样本上测量，不能据当前单元回归推算比例。
3. 原文与 Typed MathIR 语义对应仍由结构翻译/来源证据契约负责，Lean Kernel 不证明自然语言等价。当前保持 `semanticAlignmentKernelProven=false`；后续应在契约明确后补充可审计的来源对齐证据。
4. 正式 App V2 发布/安装责任仍在稳定 `main` 打包流程。当前核验的是开发工作树 Swift 编译；如需交付安装版，应从稳定 `main` 重新打包并按既有发布脚本安装，本轮不覆盖归档 App。
