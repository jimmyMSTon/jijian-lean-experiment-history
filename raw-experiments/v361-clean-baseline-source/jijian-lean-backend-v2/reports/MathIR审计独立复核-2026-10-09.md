# MathIR 原文忠实性审计：独立复核意见（2026-10-09）

## 判定

**研究报告可采纳，作为下一阶段的风险地图；没有产生生产 MathIR 能力升级。** 本复核仅核对报告、部分源代码与 Git 工作树，不执行真实 AI 请求或修改生产逻辑。

### 核实的真实问题

- `Statement Lock` 固定的是首次 MathIR AST 被解释为 Lean 后的语义，不能反向证明它与自然语言原文逐字/逐数学语义相同。
- `validate_mathir` 的 sourceRef/range、依赖和作用域合法性检查并不等于来源文本语义支持检查。
- `validate_inductions` 缺结构时的中文线索与 `canonical_plan` 的“平方/非负”、多项式类型推断均有样本/措辞相关逻辑；不能当成全题型、全语言保障。
- 图片录制的位置证据通常不足以支持精确到单字符/笔画的荧光定位。

### 报告须修正的一点

`MathIR.formal` 在 `backend/models.py` 是 optional，`UnderstandingService.structure()` 不强制 `formal` 存在。但正式 `Services.structure()` 在返回已保存的 mathir 结果前**无条件执行 `Compiler(ir)`**，它最终进入 `canonical_plan()`，若 `formal is None` 则抛出 `STATEMENT_DRIFT`。因此**不能断言生产 `/api/structure` 在缺少 typed AST 时会返回成功**。更准确地说，数据模型/中间函数允许草稿，但正式 API 当前拒绝不可编译的草稿并保存 `unvalidated_mathir` 诊断；是否把草稿公开成独立状态属于待确认的产品/数据契约决定。

### 另外一个实际交付风险

现有尚未提交的 `UI_STATE_MATRIX.md` 补充记录提及最近一次正式 App 打包环境采用 `uvicorn==0.39.0`，而 `requirements.txt` 和 `pyproject.toml` 锁定 `uvicorn==0.48.0`。目前**这是构建记录指出的版本差异，并非本次单独重建确认**。正式分发前需恢复依赖一致、可重复的构建流程，不能只用 App 成功启动和 ad-hoc 签名覆盖这个风险。

## 下一步建议（不构成自动改动指令）

1. 当前报告归档，暂停继续做同一问题的泛泛审计。
2. Codex 的下一轮开发应围绕**真实用户实际操作**，优先定位正式 SwiftUI 的“打开 → 输入 → 验证 → 查看逐步结果 → 修改 → 重验 → 历史”中具体可复现的缺陷；不依赖 UI fixture 宣称正式产品可用。
3. MathIR 线采取可落地的小步工作：首先研究如何利用**已有的 sourceRefs、Source blocks、AST、scope** 产生不篡改证明结论的只读差异证据。涉及正式 schema、成功语义、额外 AI 调用和人工确认流程的变动，先让用户决定。
4. Mathlib 上下文无损去重已位于本工作树 commit `6ca4f1b`；未做新的真实 DeepSeek/Kernel 对照，不能宣称省 Token 与模型表现实际提升。
5. 工程效率上，每轮在已有证据与源码中聚焦一项清楚的问题并形成可复现结果，减少长时间重复审计。不得由此推导新的调用次数限制、Gate 或数值验收指标。

目前 `codex/next` 还存在未提交的 UI fixture 修复（`UI_STATE_MATRIX.md`、预览 Swift 源码、预览构建和脚本）；这些改动属于其他任务，不随本复核混合提交。保持稳定 `main`、真实后端与 Kernel 不变。
