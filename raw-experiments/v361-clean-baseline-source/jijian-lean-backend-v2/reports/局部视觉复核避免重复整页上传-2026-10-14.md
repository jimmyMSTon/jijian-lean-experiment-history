# 局部视觉复核避免重复上传整页原图

日期：2026-10-14  
基线 HEAD：`f0663f556bd493461ed62482d6f466c1356a5dfd`

## 根因

`FlashVision.check_disputed_regions` 对每个存在差异或 review target 的源块分别发起局部视觉复核，但先前仍把完整原图作为该请求的第一张图片；父级源块裁切和细节裁切又作为附加图发送。整页原图在每个区域请求里重复上传，没有为该单块复核增加新的原图证据。

保存的同一用户图片视觉复测记录了 7 个待复核源块。修复前完整流程的实际 7 次请求在细节识别阶段中断，故那些局部争议复核并没有在真实运行中发生。以下数量是依据已保存 target 数和当前代码路径的静态推导，不是修复前后 live 实测：如果完整流程到达局部复核阶段，整页图会随 ImageTranscription、全局 TranscriptionCheck 和 7 个单块复核上传，共 9 次完整图像附件。

## 修改

`backend/providers/vision.py` 的局部复核现在以该来源块的父级原分辨率裁切作为 `imageNumber=1`，同请求只附加其子裁切；父级图仍留在 `cropEvidence` 中以保留 regionId、几何与来源记录，但不会作为第二张图片重复附加。局部上下文标明 `sourceImageScope="source_region"`，Prompt 明确第一张图是单个源块而非整页。模型只看到局部 block index `0`，服务端仍负责映射回原文块，不把全局索引暴露给模型，也不合并不同块的视觉证据。

另将局部映射结果显式保存在每条 `regionalChecks`：`sourceRegionId`、`sourceCropAssetId`、`detailRegionIds`。对历史 parent crop 缺少 regionId 的记录，生成与 detail grouping 共用的确定性键 `source-block-{index}`，只用于本地来源关联；不改变识别文字和数学判断。

若旧证据没有父级裁切图，代码继续退回完整原图执行复核，不跳过检查。公式/行裁切、子裁切、识别修订和差异应用规则未改。

对同一个 7-target 流程，调用数预计仍是 17（3 个初始识别/全局检查、7 个按源块分组的细节识别、7 个局部确认）；完整流程的整页附件数从 9 降到 2 是代码路径推导。后述 one-target live smoke 证明新的局部请求只发父裁切，但不等于完整 7-target 流程的 post-fix live 测量；不能声称真实 Token 或请求成本下降了特定比例。

## 验证

新增的 fixture 测试创建两个不同来源块和各自 detail crop，直接经过真实 `FlashVision.check_disputed_regions` 与 `FlashVision.check` payload 构造，断言每个请求只含自己父块与子裁切，不含整页；父子 regionId 和 `regionalChecks` 的 asset/region 映射均保留，不暴露 originalBlockIndex，跨块没有混合。`tests/test_transcription_evidence.py`：`38 passed`。

全非 live、非 `lean_local` 回归：`499 passed, 5 skipped, 21 deselected, 0 failed`；5 项跳过来自本机 Live/Runtime 集成条件未配置；1 条既有 Starlette/AnyIO 弃用警告。`compileall` 与 `git diff --check` 通过。该代码修复和回归本身没有 Provider 请求。

修复前保存的真实请求审计在 `user-samples/proof-20261013-001/v2-retest-evidence/.../20261013T183721Z-eaf59f94ca1a/`：7 次尝试、6 个模型响应、1 次因主动中断而失败，retry=0；21,291 输入 / 41,673 输出 tokens。该记录没有实际到达局部争议复核阶段，不能当作本修复后的视觉识别或 Kernel 验证证据。
