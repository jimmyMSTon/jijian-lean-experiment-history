# 原证明忠实性与多模态来源闭环（2026-10-13）

## 范围与基线

本轮从 `codex/v2-full-chain-convergence` 的 `cd1d00ccc3d6a0709430989c533acb663a22ee41` 接续，只改后端与测试，没有修改 SwiftUI、Native 页面、正式 App 包或已安装 App，也没有触发 DeepSeek。禁止合入的 `221883a` 研究分支未触碰。

本轮修复来源证据映射、非空来源区间校验、Lean Runtime 完整性误报和 Lean 批量导出诊断分类。Statement Lock、ProofLock、数学命题、前提、ProofTerm、路线依赖语义、独立 Kernel 和信任边界均未放宽。

## 根因与修改

1. **旧识别记录的人工修订没有稳定进入 MathIR 来源证据。** `RecognitionService.correct` 只在原记录已有 `transcriptionEvidence` 时写修订证据；旧记录可能只保留顶层 correction，后续 resolve 丢失它。现改为总是写不可变修订证据，保存原识别文本、规范化修订文本、`revisionOf` 和仅由用户提交的 `userCorrections`。
2. **缺失的修订父记录可能被伪装成原稿。** 若修订记录没有可恢复的 raw transcript，旧逻辑会退回当前修订文本。现将 `raw` 留空，并显式给出 `sourceRevisionEvidenceMissing` 和 unmapped ambiguity，不再声称当前文字就是可核对的原稿。
3. **混合输入和 PDF 的局部索引会错映到聚合文本。** 混合来源中，前面的文字片段会改变后续图片的总 block 下标；PDF 每页的局部索引也不能当成全 PDF 索引。现在根级 `sourceMappingVersion=1` 证据以稳定 `blockId` 为准；混合来源保留每个识别子项的 `partIndex`、`sourceBlockIds`、`sourceBlockIdMap`、`assetIds`；PDF 保存 `pageBlockMap`（页码、页 assetId、来源 block ID）。无法映射的条目明确保留为 unmapped，不生成虚假的 SourceRef。版本化根证据是规范列表，转换时不再重复递归追加子记录。
4. **零长度 SourceRef 曾被接受为“有来源”。** 现在必须满足 `0 <= start < end <= block.text.length`；空区间返回 `V2_SOURCE_REF_RANGE`。同时为已有的重复 source block ID 拒绝逻辑补上回归覆盖。
5. **LeanRunner 曾只用 `Audit.olean` 是否存在判断 Runtime 就绪。** 这会把没有锁文件、协议可能过期的源码目录误报为可运行。本轮 `info()` 必须读取 `.jijian-source-lock.json`、核对 `jj_export:nonce:name:type:proof` 协议、三个编译模块 `Wire/Export/Audit` 的 SHA-256，并在打包环境核对 `JJ_RUNTIME_SOURCE_FINGERPRINT`。返回新增 `runtimeIntegrity`、`runtimeAttestation` 字段。缺少证明材料时 readiness 为 false；不触碰或删除旧 `.olean`。
6. **Expected-type 批量导出中的 proof 错误会污染固定命题状态。** 同一 Lean 命令可能已经输出有效的 `JJ_EXPECTED` 类型 wire，之后才在 proof candidate 上报错；此前无差别加入 batch-global proof diagnostic 会把有效 statement 误归为形式化失败。现保留每个 expected nonce 的 scoped diagnostics；有效 expected wire 不因后续 proof 阶段错误而被改写为 statement failure，proof 错误仍由 proof marker 独立判定。

后端证据字段是向后兼容的附加信息。Native 可继续只使用既有 `recognitionId`；如后续需要精确恢复混合来源，可读取 `partIndex`、`sourceBlockIds` 与 `assetIds`。没有改动 Native 数据消费代码。

## 原证明性质与剩余边界

| 性质 | 本轮可复核结论 | 证据类别 |
|---|---|---|
| 正确不等式与已声明前提 | 完整路线、依赖使用和 Kernel 均通过 | 本轮真实 Lean/Kernel，测试构造输入 |
| 错误不等式方向 | 原命题保持不变；Lean 不能证明，标为 not established；没有反例证书 | 本轮真实 Lean/Kernel，测试构造输入 |
| 错误代数/错误关系 | 错误 `1=2` 不能借助无关的 `2=2` 通过；原路线依赖检查失败 | 本轮真实 Lean/Kernel 对照 |
| 断裂、无关步骤、未使用依赖 | 固定目标可独立通过时，仍拒绝把不完整原路线标为通过 | 本轮真实 Lean/Kernel 对照 |
| 归纳假设依赖 | 归纳步单步可证不等于正确使用 IH；未用 IH 时完整路线不通过 | 本轮真实 Lean/Kernel |
| 量词与较复杂正确证明 | 复用既有 C07 等保存证据；未在本轮重新请求模型或重跑同题 | 历史本机 Kernel 证据 |
| 图片、混合来源、PDF | asset、识别记录、页/part/block 映射和修订差异通过本地确定性 fixture 检验 | fixture；不是视觉 AI 实测 |
| 中文/手写原稿与 MathIR 的语义等价 | 仍未由 Kernel 证明，`semanticAlignmentKernelProven=false`；来源映射准确不等于数学语义等价 | 明确保留的可信边界 |

本轮没有让模型补写用户证明，也没有删掉错误步骤或用目标单独可证代替原路线。未产生新的数学反例证明；Lean 无法证明仍只表示当前 proof obligation 未建立。历史 C01/C07/C08 等成功记录保持原证据等级，没有冒充本轮新鲜模型/视觉测试。

## 尚待处理的真实问题

- **语义对齐仍需独立证据：** 后端能持久化 raw transcript、修订与稳定来源位置，但 Kernel 不证明自然语言/图像步骤和 Typed MathIR 等价。若模型结构化改变命题，必须依靠更强的语义对齐审计契约或明确用户校对，不能将 Kernel 通过解释为原文忠实证明。
- **本机源目录旧 Lean build 不再被信任：** 从默认 `lean-runtime` 目录直接启动后端会显示 Lean 未就绪，这是对缺锁旧 OLean 的明确诊断。开发/打包时应使用 `scripts/prepare_runtime.py` 生成的源码匹配 Runtime，并将 `LEAN_PROJECT_DIR` 与对应 `JJ_RUNTIME_SOURCE_FINGERPRINT` 交给后端。
- **本轮没有真实视觉 DeepSeek 或真实用户 GUI 测试。** 图片识别校对、历史重开和修改重验 GUI 由 ChatGPT Native 工作流负责；后端这里只验证了来源合同与 fixture。
- **耗时仍明显受 Lean 初始化影响。** 断裂/依赖对照中多个 Lean 独立阶段耗时较长；本轮没有删除独立 Kernel replay、依赖审计，也没有可比的模型 E2E 性能样本。不能据此报告总体速度提升。
