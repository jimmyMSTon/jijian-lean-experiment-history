# 真实证明盲测样本交接格式

本文件供 ChatGPT 与 Codex 交接真实学生证明样本。它说明现有盲测工具的输入字段与证据位置，不增加产品流程、题型限制或成功门槛。

## 单样本目录

将原始文件、机器输入清单和独立参考结论分开保存。例如：

```text
user-samples/<case-id>/
  manifest.json
  proof-original.jpg
  independent-reference.json
```

原图/原文件应保持原始字节。样本清单中的 `expectedSha256` 填写该原始文件的 SHA-256；运行器会在保存图片资产或调用视觉模型前比对它。没有原图时不要用相似图片替代，也不要把人工转录标成视觉识别结果。

## 机器盲测清单

当前工具 `scripts/run_user_proof_blind_case.py` 接受 `jijian-lean-blind-case-v1`。图片样例：

```json
{
  "format": "jijian-lean-blind-case-v1",
  "caseId": "student-proof-2026-01",
  "input": {
    "kind": "image",
    "file": "proof-original.jpg",
    "expectedSha256": "把64位十六进制原图SHA-256放在这里",
    "corrections": []
  },
  "referenceFile": "independent-reference.json"
}
```

例子中的 SHA 占位文字需替换为 64 位十六进制摘要。没有用户校对时 `corrections` 留空；用户校对后，按识别版本的 blockId 和 Unicode 码点半开区间写入 correction，保留 `expectedText` 与 `replacement`。不要提前把修订文本伪装成模型识别文本。混合输入可使用 `input.kind="mixed"` 和按原稿阅读顺序排列的 `parts`；每个 part 类型为 `image`、`text` 或 `strokes`。文字 part 是已确认输入，不能再附 recognition corrections。

人工参考结论必须仅放在独立 `referenceFile` 中，不能放入 manifest、输入文本、图片说明或任何发送给 Provider 的文件。运行器拒绝 manifest 内出现参考答案类字段，并拒绝参考文件与 manifest/输入图片复用同一路径。参考结论在完整盲测结果持久化后才读取。

参考文件字段没有被盲测工具强制成固定 schema。建议至少记录：独立判定（正确、存在错误、未完成或存在歧义）、原稿错误/未建立步骤、理由，以及参考者和判读备注。证据不足时写明不确定，不把“未找到证明”记为“已证明命题为假”。

## 运行后核对的证据

每次运行都会创建独立、权限收紧的运行目录，并保存：

- `run-started.json`、`workflow-status.jsonl`：Git HEAD、manifest 摘要和运行状态；
- `source-files.jsonl` 与 `runtime-data/assets/`：输入部件、原始 SHA-256、资产 ID 和原始图片字节；
- `recognition-checkpoints.jsonl`：初始/最终 recognitionId、原识别文字、校对文字、稳定 blockId 与修订记录；
- `blind-result.json`：Runtime 指纹、请求审计、source structure、最终 Typed MathIR、statement hash、proof route、Lean diagnostics、Kernel/依赖结论和工作流终止状态；
- `runtime-data/mathir-v2-evidence/`：按内容寻址的 proof wire 与其他完整证据；
- 若配置了独立参考，`reference-comparison.json` 保存盲测结果和参考文件的哈希，初始状态为 `pending_human_review`，不会自动替代人工对照。

审阅时分别判定图片识别、用户校对、MathIR 语义、SourceRefs、obligation、原步骤依赖、Lean 和 Kernel。Kernel 只验证锁定的形式命题与证明；即使 Kernel 通过，也不表示图片或中文原稿与 MathIR 已被证明语义等价。MathIR 编译失败、缺 proof、Lean 未证明和系统异常必须保留各自状态。

本工具可用历史真实样本和本地 fixture 测试，但 fixture 只能证明数据契约；只有运行审计中的 `realRequestAttempts`、完整模型响应与明确的真实 Lean/Kernel 证据，才能分别报告为实际模型或内核结果。
