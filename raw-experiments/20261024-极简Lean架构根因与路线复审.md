# 2026-10-24｜极简 Lean 验证主体架构根因审计（不是普通 Bug 清单）

## 结论
目前不是单纯 DeepSeek 证明能力不足，也不是 Lean Kernel 可靠性问题。**源证明→AI MathIR 步骤结构→Lean 子命题** 的忠实性没有成立：系统接受了“原稿数学条件已经丢失或特定构造被全称化”的 MathIR，而后一层 `ProofLock` 又把这些错误子命题冻结，让模型只能对假目标补 `proofTerm`，不能修正前提或结构。此时再多次生成、检索、修复都无法成功。

原稿定理本身并未被 Lean 否定；Lean 恰恰帮助我们证明系统自行生成的两个子目标是假的。

## 真实回归数据
- 同一个正式包 `868349bf1fbec7ffae5e45c01d671f3552ba56d2`，最新原文三题并行真实 DeepSeek/Lean，共 **25 API requests、771,073 input + 478,282 output Tokens、完整通过 0/3**。
- 数论 13 请求、7/11 形式步骤通过、余 4 个节点无正确证书；IVT 10 请求、16/17 步骤通过、`N_c_sup` 无证书；谱定理 2 请求、类型未决，未进入 Lean。
- 这些正式结果不是“DeepSeek 直接写 Lean vs 当前 MathIR”的对照实验，所以不能直接宣称纯 DeepSeek 必胜；但两个假目标的发现，已经足以证明当前 IR 路线**客观地阻止了成功**。

## Kernel 证实的致命错误 A：数论的前提丢失
原稿：有限多个 `p_i` 均为模 4 余 3 的素数，所以正整数积 `P≥1`，令 `N=4P−1`，推出 `N>1`。

正式 DeepSeek MathIR 中 `a_finite` 是独立 `local_assumption`，而 `c_N_gt1.dependsOn=[]`。服务端编译了：

```lean
∀ (r : ℕ) (pseq : ℕ → ℕ),
  let P : ℕ := ∏ i ∈ Finset.Icc 1 r, pseq i
  let N : ℕ := 4 * P - 1
  N > 1
```

这样 `pseq` 被错误当作**任意自然数列**；取 `r=1`，`pseq(1)=0` 得 `N=0`，结论不成立。

独立 Lean Kernel 已成功证明这个**完整生成子目标的否定**（fresh environment + statement identity + 无额外公理）。失败原因不是 DeepSeek 不会证明初等数论，而是让它证明了错误的数学命题。数论其他缺失节点也有同类风险，但不能未核查即宣称全部是假命题。

## Kernel 证实的致命错误 B：介值定理的上确界定义变成全称证明
原稿：由非空、有上界，**定义/选取** `c=sup S`，再推导 `0<c<1, f(c)=0`。

正式 MathIR 中 `decl_c_proof` 是 `scope_proof_c` 中**没有 value 的普通自由变量**；`N_c_sup` 要求 `IsLUB S c`。编译器封闭自由变量后给出了 `∀ c : Set.Icc 0 1, IsLUB S c`（前提中虽包含 `S` 非空、`S ⊆ Set.univ`，但没有固定这个 `c`）。

取合法连续函数 `f(x)=x−1/2`，`S={x∈[0,1] | x<1/2}`，再取 `c=0`：0 不是 `S` 的上界。该**完整生成子目标的否定**同样已获真实 Lean Kernel 证书且没有额外公理。

这说明 `16/17` Lean 单步通过率是误导性的：缺的 1 步在已锁定 MathIR 中是假的，**成功率无法靠多重试来补齐**。本案的区间函数类型虽然已在最近版本修复，错误的“任选上确界”这一核心语义却一直没有修复。

## 架构问题 C：错误 IR 被锁定，repair 无权修正
代码路径：`backend/v2/service.py` 先从结构模型取得 MathIR，再 `compile_v2` / `create_proof_lock`；`backend/v2/proof_only.py` 的 `_assert_lock` 在之后禁止改动声明、前提、目标、dependency、scope。`backend/v2/workflow.py` 的修复仅接受 `proofTerm` patch。

因此遇到假目标时，模型**不能恢复原稿中遗漏的素数假设、不能将任意 c 改为定义的 Sup S**。它只能继续猜 tactic，直到根据 prompt “若没有忠实证明，省略 nodeId”返回空补丁并停止。`proof_generation_returned_no_patch`、`proof_generation_after_repair_returned_no_patch` 恰是此处的症状，不是独立根因。

## 架构问题 D：自造类型语言无法可靠承载一般高等数学
`backend/v2/models.py` 的 Vector.dimension / Matrix.rows / Matrix.cols 是固定非负整数；用户谱定理维数是变量 `n`，并有 `n−1` 的归纳重绑定。结构模型只能绕路用参数化 TypeApplication/TypeVar 与大量 scope/binder 约束。最新谱定理真实失败 `V2_TYPE_DOMAIN_UNRESOLVED`，向量变量 `tv_vec_step` 候选为空。Lean/Mathlib 原本就有 `Fin n → ℝ`、`Matrix (Fin n) (Fin n) ℝ` 等成熟依赖类型，当前 IR 相当于重做一套 Lean 类型系统，增加且扩大了错误来源。

## 架构问题 E：原稿推理认证器不是通用数学证明判定器
`backend/v2/reasoning_fidelity.py` / `source_inference.py` 目前只实现了一批专门的等式、量词、谓词、极限等来源规则。最新 23 个已过 Kernel 的局部步骤（数论7、实分析16），来源独立认证 **0 个**。Kernel 证明某个命题是真的 ≠ 证明作者用了同一条推理；但规则器覆盖远小于实际数学证明领域，也不能把全域原稿判定能力建立在无穷增长的手写规则之上。

## 第一性原理下的路线决策
用户输入的是人类证明；输出应是“作者写的结论及每个核心推导是否有数学证书；系统补全了哪里；哪里仍未证实”。我们目前做成了“让 AI 先发明一张必须全证的中间命题图，再逼另一个 AI 逐个完成”。**路线已经偏离**，而且这条偏离有上述两个 Kernel 反证，不只是主观判断。

### 建议以最小形式化主体重新开始，而不是继续增补旧 IR
1. **简化 MathIR** 为 source anchors / 原稿核心步骤文本 / 显式假设与绑定 / candidate Lean expression / provenance。不要试图再靠 Python AST 重现完整数学语义、构造器与无数特殊运算；让 Lean/Mathlib 检查真正的类型系统。AI 仅建议符号、Lean 声明及证明项。
2. **先验证“源命题→候选 Lean 命题”**，区分原稿明确写的假设、作者定义和模型引入的辅助构造。每个 proof obligation 不能漏依赖或把 `let c := Sup S` 变成 `∀ c`。不忠实的候选必须回到语义形式化阶段，不能锁错后继续 proof-only。对无法自动确认的变换明确显示未证实，不伪称独立认证。
3. 仅对**有来源、类型可 elaboration、目标数学语义可信**的子步骤运行 Kernel 验证。简短原稿的缺省步骤可由 AI 写补充形式证明，但需明确标示“AI 补证”，与作者原稿推理分开。整个 formal proof 与 source proof 是两个不同结果。
4. 在隔离的重构验证链上与现版做**控制变量 A/B 基准**，包含三道原始难题及简单/正确/有错证明。指标是整题 kernel verified、命题/假设忠实、作者推理已证比例、未说明推理、总请求/token 和耗时。不得把新的源程序通过单测数量当作突破。未证实新链路可靠前不覆盖正式 App。
5. 当前不应再对两条已被 Lean 证明为假的 IR 子目标付款重试。先替换这条架构路径。
