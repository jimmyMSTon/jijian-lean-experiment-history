## 二、已确认的产品接入契约断点

1. **提交路径不同**。正式 NativeStore.swift:287 指向 /api/jobs；研究 V2 另设 /api/v2/jobs。不是只重编译 V2 后端就能升级现有 App。
2. **返回包不兼容**。V1 Services.pipeline 返回 verificationId、formalizationId、mathIR、feedback 等。V2 MathIRV2Service.pipeline（backend/v2/service.py）返回持久化 mathir_v2_run，含 status、termination、failure、verification、events、mathIRId、fixedStatementKernelPassed、originalRouteKernelPassed，且**没有** V1 的 verificationId/formalizationId/feedback。NativeStore.swift:393-399 hydrate() 会根据 verificationId/formalizationId 去读 V1 artifact；因此不能直接把提交 URL 改成 /api/v2/jobs。
3. **结果数据模型不兼容**。Native/BackendClient.swift:110-165 的 ProofRecord 读取 mathIR.goal.text、feedback.items、verification.steps[].stepId/established/status，以及 status=formal_verified、originalMeaning。V2 compact_verification 返回 routes[].steps[].nodeId、status、proofAttemptStatus、dependencyEvidence、Kernel 证书和 originalRouteKernelPassed；V2 mathIR.goal 是结构化表达式而不是单独的 V1 goal.text。两边需要明确的展示数据适配；不可通过假字段伪造 success。
4. **历史记录不兼容**。NativeStore.swift:411-466 通过 /api/history 默认 kind=verification 读取 V1 verification/formalization/feedback；V2 run 写入的是 mathir_v2_run、mathir_v2 和 mathir_v2_draft。现有历史页不会自动列出 V2 验证记录。
5. **进度事件不一致**。NativeStore.swift:332-346 特判事件 structured 以提取 mathIRId；V2 发送 mathir_v2_structured、proof_workflow_started、lean_verification、mathir_v2_completed 等。当前 UI 状态与 source-mapping 取数流程需要映射。
6. **旧图片复核链路不同**。Services.pipeline（V1）在 Kernel 不通过且来自图片时，调用 review_failed_steps 并保留 imageFailureReview。当前 V2 MathIRV2Service.pipeline 无对应失败后区域复核路径。是否需要迁移既有机制是产品行为兼容性问题，先报告事实，不自动新增阻断。
7. **成功语义需忠实呈现**。V2 用 completeOriginalRouteKernelPassed/originalRouteKernelPassed 等不同层级；V1 Native 的 ProofRecord.verified 判断 kernelVerified、formal_verified、simulated、ambiguities、每步 established。不能把 V2 的 HTTP/job completed 或单个 fixedStatementKernelPassed 直接映射为用户“原证明已通过”。

以上均为当前源码核查结论，不是现场 V2 真机 E2E 通过证据。

## 三、已经证实的历史性能责任
- 正式 V1 一次简单修改后的验证耗时约 442s；9 次 DeepSeek 请求；407,018 输入 tokens / 36,130 输出 tokens，Repair 贡献 390,879 输入 tokens（来源：reports/Repair上下文膨胀与成本优化V2-2026-10-10.md）。主要责任是 Mathlib 检索证据重复传输/工作流设计，不是 Lean Kernel 数学错误。
- 之前已经做过同轮多步骤 ProofBodies 合并：真实对照保留全部检索证据，首次两个步骤合计输入 token 降低约 49.7%，且后续 Kernel 通过。不得说这项优化尚未实施。
- 同一保存等式 proof 批量 Lean 进程由 5 组变为 3 组，68.1s 降至约 41.5s；进程最大 RSS 仍约 5772 MiB，物理 footprint 约 891 MiB（来源：reports/MathIR-v2-stage6-Lean进程治理与Mac集成风险.md）。已解决一部分无效重复启动问题，不能直接将剩余耗时全部归因于 DeepSeek。
- V2 真实模型自动端到端的成功率不能从 C01/C07/C08 的保存补丁回放推出；HTTP 402 为 Provider 账户/服务错误，不是模型数学能力评价。

## 五、当前确定的结论
- 当前 V2 研究后端**没有交付进正式 Mac App**。
- 研究 V2 API 与现有 Native SwiftUI 的数据模型**并不兼容**，直接换路由无法使用。
- 真正急需的工程不是继续修一批固定题，而是把 DeepSeek/MathIR/Compiler 的实际责任查清，并让已经有证据的能力形成真实用户可用的交付。
- 本核查不宣布 V2 全系统完成，也不宣布现有框架值得或不值得继续。后两者取决于完整实际对照证据，未验证部分标为未验证。

## 六、外部复用项目核查（公开资料，未在本机安装）

1. LeanTutor 官方网站 https://leantutor.org/ 已公开自由格式/手写证明输入、逐步 Lean 引理转化、证明组合、自然语言反馈、形式解释与修改再验证。**它是直接竞品，不能再将这些功能当作独占壁垒。** 官方网站功能展示不等于开放可直接复制的全部源码，本次未核实 LeanTutor 完整产品代码可复用。
2. Math Inc OpenGauss https://github.com/math-inc/OpenGauss 公开 MIT 许可。官方 README 明确其本体是项目级 Lean 工作流编排器，实际证明/formalize 工作流来自 cameronfreer/lean4-skills，并非原证明可信性产品端到端的即插即用替代。
3. lean4-skills https://github.com/cameronfreer/lean4-skills 公开 MIT 许可，支持 Codex、Lean LSP/MCP、draft、formalize、autoformalize、prove、autoprove、review、disprove 等。可作为研发侧证明生成/Lean 检索和 proof repair 的可选复用能力进行隔离比较；它的源命题起草与证明补全工作流需防止改写用户原来的数学前提与推理。
4. **技术判断**：OpenGauss/lean4-skills 可以作为对照的证明执行引擎；不能仅因它能从自然语言生成 Lean 就认定其忠实核验用户原证明。LeanTutor 有直接竞品价值但本次没有可直接复用的源码证据。
5. 未安装任何第三方程序，未修改 DeepSeek 模型设置，未触发模型费用。保留正式 DeepSeek 与 V2 作为当前产品路线；以上仅为替代技术的研究素材，不是自动替换决定。
